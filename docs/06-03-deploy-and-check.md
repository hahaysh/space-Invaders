# 06-03. PR·병합·배포 결과와 공개 URL 확인

**6. 배포 · 최초 버전 공개**

이전: [06-02 Actions 워크플로](06-02-actions-workflow.md) · [전체 목차](00-overview.md) · 다음: [07-01 변경 요청](07-01-change-request.md)

## 1. 설명

로컬 커밋, 원격 푸시, PR 생성, PR 병합, Pages 배포는 별개의 사건입니다.
**PR을 만들었다고 `main`에 반영되거나 배포되는 것은 아닙니다.**
이번 단계에서는 각 승인 경계를 거쳐 최초 버전을 공개하고 실제 URL에서 확인합니다.
외부 CLI나 VS Code를 열 필요는 없습니다. app에 작업을 요청하고 GitHub 웹에서 확인합니다.

### 앞 단계에서 이어지는 배포 과정

| 순서 | 수행 위치와 행동 | 다음으로 넘어갈 근거 |
|---|---|---|
| 06-01 | app에 준비 점검 요청, 참가자가 GitHub 웹에서 Pages Source를 GitHub Actions로 설정 | 자신의 게임 저장소·공개 범위·환경 확인 |
| 06-02 | app에 계획·생성 프롬프트 입력, 에이전트가 `pages.yml` 작성 | 워크플로 diff와 로컬 테스트·빌드 검토 |
| 06-03 푸시·PR | app에 승인한 게임 브랜치의 푸시·PR 생성 요청 | 실제 PR의 검사 결과와 최종 diff 확인 |
| 06-03 병합 | 참가자가 별도로 병합 승인 | `main` 반영으로 Actions 배포 실행 |
| 06-03 확인 | app에 실행 상태 확인 요청, 실제 Pages URL에서 게임 조작 | 배포 SHA·URL·게임 동작 증거 |

배포 서비스는 **GitHub Pages**, 이를 자동으로 수행하는 도구는 **GitHub Actions**입니다.
app의 에이전트는 워크플로 작성과 GitHub 작업을 돕지만, 게임을 에이전트 세션 자체에 게시하는 것은 아닙니다.

## 2. 시작 상태

- [ ] 06-02의 파일이 로컬 커밋되었고 테스트·빌드가 통과했다.
- [ ] Pages Source·환경 규칙을 확인했다.
- [ ] Public 저장소에 올릴 코드·문서·이력에 민감 정보가 없다.
- [ ] **Plan** 모드에서 저장소·세션 브랜치·원격·`main`을 확인한다.

## 3. 실행: 푸시와 PR 생성 승인

```text
현재 참가자 게임 저장소에 생성한 GitHub Actions 워크플로로
이 게임을 GitHub Pages에 배포하기 전 읽기 전용 점검을 해줘.
AGENTS.md, TEST_RESULTS.md, .github/workflows/pages.yml을 읽어줘.
git 상태와 커밋 조회는 허용한다.
현재 작업 브랜치가 main과 다른지, 승인한 커밋이 모두 있는지 확인해줘.
Pages Source=GitHub Actions와 github-pages 환경의 main 허용 여부는
직접 확인 가능한 정보와 참가자가 전달한 확인 결과를 구분해줘.
원격 설정이나 필수 로컬 검증이 미확인이면 배포 준비 완료라고 말하지 마.
아직 배포하지 않은 공개 URL 확인은 이번 단계의 후속 검증으로 구분해줘.
푸시 대상 원격/브랜치, PR의 head/base, 공개할 변경과 미검증 항목을 제시해줘.
파일 수정·fetch·푸시·PR 생성·병합은 아직 하지 말고 기다려줘.
```

참가자가 대상과 diff를 확인하고 **Interactive**로 전환합니다.
아래의 “방금 확인한” 대상이 모호하면 실제 저장소와 브랜치 이름으로 바꿉니다.

```text
방금 확인한 Public 저장소와 기능 브랜치로 승인 커밋을 푸시하는 것을 허용한다.
해당 브랜치에서 main으로 PR을 만들어줘. 필요한 git/gh 작업은 이 범위에서 허용한다.
직접 main에 푸시하거나 강제 푸시하지 마.
PR 본문에 REQ-01~08 구현 범위, 로컬 검증 결과, Pages 공개 목적을 적어줘.
PR URL과 원격 검사 상태를 알려주되 병합·후속 수정은 하지 말고 기다려줘.
```

app의 PR 화면 또는 반환된 GitHub PR URL에서 변경 파일과 CI를 확인합니다.
app에서 PR 생성이 지원되지 않으면 브랜치 푸시 후 GitHub 웹의 PR 생성을 사용합니다.
PR 검사에서는 build만 실행하고 deploy는 건너뛰는 것이 정상입니다.

### 병합은 별도로 승인하기

```text
PR의 최종 diff와 검사 결과를 읽기 전용으로 점검해줘.
실제 PR 번호, head 커밋, base main, 테스트·빌드 결과를 제시해줘.
실패·대기·미확인 검사나 미해결 리뷰가 있으면 병합하지 말고 알려줘.
```

점검이 통과하면 GitHub 웹에서 참가자가 **Merge pull request**를 실행하거나,
다음처럼 app에 정확한 PR을 지정하여 병합을 요청합니다.

```text
방금 확인한 PR과 최종 head 커밋의 main 병합을 승인한다.
검사가 달라졌거나 새 커밋이 추가됐다면 멈추고 다시 검토를 요청해줘.
보호 규칙 우회 없이 병합하고, main push로 시작한 Actions 실행 URL을 알려줘.
병합 커밋 메시지도 구체적인 한국어 제목·본문으로 작성하고,
단계 ID 06-03, 반영 내용·이유, 검증 결과와 아직 미확인인 공개 동작을 적어줘.
배포 완료와 공개 URL 확인은 별도로 보고하고 다음 실습을 시작하지 마.
```

## 4. 함께 점검·확인: 실제 배포와 브라우저

GitHub **Actions → Check and deploy Pages**에서 `main` 실행을 엽니다.
대상 SHA가 병합된 버전인지 확인한 뒤 build와 deploy 로그를 순서대로 봅니다.
환경 승인 대기는 실패와 다르며 지정된 승인자가 승인해야 합니다.
deploy 출력의 `page_url` 또는 **Settings → Pages**의 실제 링크를 엽니다.
`https://사용자.github.io/저장소/` 형식은 설명용일 뿐 성공 증거가 아닙니다.

app에서 다음 프롬프트로 실제 실행 상태를 함께 확인할 수 있습니다.

```text
방금 병합한 참가자 게임 저장소의 main 커밋을 배포하는
Check and deploy Pages 워크플로 실행을 읽기 전용으로 확인해줘.
실제 실행 URL과 커밋 SHA, build/deploy 각각의 상태,
완료된 경우 실제 page_url을 알려줘.
진행 중/승인 대기/실패/완료를 구분하고, 실행이 없으면 없다고 말해줘.
승인이 필요하면 어떤 화면에서 누가 무엇을 승인해야 하는지 구체적으로 알려줘.
접근 권한이 없으면 내가 GitHub에서 확인할 위치를 안내하고 결과를 추정하지 마.
재실행·설정 변경·새 커밋·푸시는 하지 마.
워크플로 성공과 공개 URL에서 게임이 정상 동작하는 것은 별도로 확인해줘.
```

| 실제 공개 URL에서 확인 | 확인 방법 |
|---|---|
| 정적 전달 REQ-08 | 반환된 주소를 새 창에서 열고 새로고침해도 정상인지 확인 |
| 하위 경로 | 저장소 하위 경로의 JS·CSS가 404 없이 로드되는지 Network 확인 |
| 시작·이동 REQ-01~02 | 제목 화면, Enter/버튼 시작, 방향키·A/D와 좌우 경계 |
| 발사·적 REQ-03~04 | Space 연사 간격 0.2초, 3행×8 적의 이동·하강 |
| 충돌·점수 REQ-05 | 적 한 개당 10점, 중복 충돌로 점수가 늘지 않음 |
| 종료·재시작 REQ-06~07 | 모두 제거 시 승리, 적 하단 y=520 도달 시 패배, R/버튼 초기화 |
| 실행 오류 | Console 오류와 외부 CDN·이미지 요청 없이 실행 |

도구로 자동 확인한 항목과 참가자가 눈으로 확인한 항목을 구분합니다.
승리·패배를 실제 확인하지 못했다면 그 항목은 미확인으로 남깁니다.
공개 사이트에 테스트 전용 조작 UI를 추가해 검증을 대신하지 않습니다.

```text
실제 확인한 배포 실행 URL, 배포 SHA, page_url, 브라우저와 확인 시각을 정리해줘.
내가 전달한 수동 확인 결과와 도구로 실행한 결과를 구분해서
TEST_RESULTS.md의 최초 배포 확인 항목에 기록하는 것을 승인한다.
관찰하지 않은 항목은 미확인으로 남겨줘. 코드·워크플로는 수정하지 마.
기록 변경만 보여주고 커밋·푸시는 기다려줘.
```

### 예상 결과

승인한 PR, 병합된 SHA, 실제 Actions 실행, 실제 공개 URL과 동작 확인 기록입니다.
기록 커밋은 배포된 코드 SHA 이후에 생기므로 두 SHA를 혼동하지 않습니다.

## 5. 보완과 재확인

```text
배포 확인이 실패했다. 실제 실행 URL/실패 단계/브라우저 오류를 기준으로 진단해줘.
npm ci, 테스트, 빌드, 환경 승인, OIDC 권한, 경로 404를 구분해줘.
수정 후보와 영향 범위를 먼저 제시하고 파일 변경은 승인까지 기다려줘.
main 직접 수정·강제 푸시·보호 규칙 해제·실패 무시는 하지 마.
```

- 검사 실패: 해당 로그의 최초 오류를 고치고 로컬 재검증 → 수정 PR로 진행합니다.
- 배포 실패: Source, `github-pages`의 `main` 허용, deploy 권한과 artifact를 확인합니다.
- 흰 화면·404: 실제 URL 하위 경로와 Vite `base: './'`, `dist` 내용을 확인합니다.
- 오래된 화면: 배포 SHA와 새로고침·캐시를 확인합니다. 성공 로그만 믿지 않습니다.

수정 커밋을 올리는 경우에도 푸시·PR·병합 승인을 다시 받습니다.
원인 없이 워크플로를 반복 실행하거나 검증 단계를 제거하지 않습니다.

## 6. 완료 승인

- [ ] 최초 버전 `main` 배포와 공개 URL을 실제로 확인했다.
- [ ] 수동 결과·자동 결과·미확인 항목을 구분했다.
- [ ] 개선 전 기준 SHA와 URL을 기록했다.

```text
최초 배포 확인 결과를 승인한다.
TEST_RESULTS.md 변경만 구체적인 한국어 제목과 본문으로 로컬 커밋해줘.
제목 예시: '06-03: 최초 Pages 배포와 공개 주소의 실제 게임 동작 확인 결과 기록'
본문에 단계 ID 06-03, 변경 내용·이유, 배포 SHA, 검증 결과·미확인 범위를 적어줘.
푸시나 다음 단계는 하지 마.
다음 개선 작업 전에 main 동기화와 이 기록 커밋 보존 방법을 확인하도록 요약해줘.
```
