# 02-03. 기술 설계

[이전](02-02-요구사항-작성.md) · [전체 목차](00-전체-실습-안내.md) · [다음: 문서 점검과 이슈 등록](03-01-문서-점검과-이슈-등록.md)

## 이번 실습

PRD를 어떤 기술로 구현하고 확인할지 정합니다.
브라우저 화면과 게임 규칙을 적당히 나누면 자동 검사와 실제 조작을 함께 확인하기 쉽습니다.
모듈 개수나 비공개 함수 이름을 미리 고정하는 설계는 하지 않습니다.

## 시작 전

- 승인한 `ideation.md`와 `PRD.md`가 있습니다.
- 02-02의 참고 자료와 실제 PRD를 대조했으며 기본 게임의 필수 수치가 확정됐습니다.
- 게임 코드와 package manifest는 아직 없습니다.
- App **Plan**으로 설계를 제안받습니다.

## 기술 선택

| 역할                 | 기본 선택                                       |
| -------------------- | ----------------------------------------------- |
| 화면                 | HTML·CSS·ES Modules, Canvas 2D                |
| 실행·빌드           | Vite, dev/E2E 5173, preview 4173                |
| 게임 규칙 검사       | Node 내장`node --test`, 제어 가능한 모델 시간 |
| 실제 입력·화면 검사 | Playwright Chromium, 실제 키·버튼 조작         |
| 공개                 | GitHub Actions에서 검증한 dist를 GitHub Pages로 |

공식 플레이 환경은 키보드를 사용할 수 있는 데스크톱 브라우저로 한정합니다.
CSS와 Canvas는 작은 viewport에서 화면 비율을 유지할 수 있지만, 이것은 모바일
터치 조작이나 모바일 브라우저 지원을 의미하지 않습니다. 터치 입력, 가상 조작
버튼, 화면 회전 대응은 현재 기술 설계에서 제외하며 별도 후속 기능으로 다룹니다.
적 탄환은 각 열의 가장 아래 적을 결정론적으로 선택해 일정 간격으로 생성하고,
플레이어 피격은 탄환 하나당 한 번만 처리합니다. 목숨·재도전·최종 패배는 모델의
명시적인 상태 전환으로 검증하며, 화면 효과만으로 피격을 판정하지 않습니다.
적이 남아 있는 상태에서 방어선 도달과 적 탄환 피격이 같은 갱신에 발생하면
방어선 도달을 먼저 처리해 `lost`로 종료하고, 해당 갱신에서는 목숨 차감이나
자동 다음 시도를 시작하지 않습니다.

## 참고 자료 전달과 기술 설계 제안

위 **기술 선택 절 전체**(표와 표 아래의 지원 환경·입력·적 탄환·판정 설명)를 복사해
아래 Plan 프롬프트와 같은 메시지에 붙여 넣습니다. 안내 파일의 자동 참조나 App의 첨부 기능을
전제로 하지 않습니다. 제품 수치는 이미 작성한 참가자 `PRD.md`에서 읽습니다.
제안이 전달한 기술 선택과 일치하는지 확인하고 같은 대화에서 작성을 승인합니다.

**모드: Plan**

```text
AGENTS.md·PRD.md를 읽고 함께 전달한 기술 선택 자료를 기준으로 TRD 구성을 제안해 줘.
기술 선택 자료를 확인할 수 없으면 필요한 자료를 알려 주고 멈춰 줘.
PRD에 화면·개체 크기·위치·속도·발사 간격·편대·점수·목숨·방어선 수치가 있는지 먼저 확인해.
미정·누락이나 기술 충돌이 있으면 해당 항목과 문서 보완안을 제시하고 멈춰 줘.
문제가 없을 때만 다음 설계를 제안해 줘.
작은 모델/UI 분리를 권장하되 과도한 계층이나 고정 함수명은 만들지 마.
상태 전환·초 단위 시간·충돌/승패 순서·적 탄환·피격·목숨·입력 정리·재시작 책임을 설명해 줘.
한 게임 루프와 중복 없는 이벤트 연결, 긴 프레임의 과도한 이동 방지를 설계해 줘.
Node 규칙 검사와 Playwright 실제 입력 검사를 구분해 줘.
데스크톱 키보드·버튼 입력을 공식 검증 대상으로 하고, 적 탄환과 피격·목숨 전환도 검증해 줘.
반응형 화면 표시와 모바일
터치 플레이를 구분해 줘. 터치·가상 버튼·회전 대응은 이번 범위에서 제외해 줘.
테스트 전용 전역 모델 API나 브라우저 치트 없이 검증할 수 있게 해 줘.
호환되는 안정판 의존성을 manifest에 먼저 정의하고 설치·lockfile을 남기는 순서로 해.
Vite base './', 외부 런타임 자산 없음, dist만 배포하는 경로를 포함해 줘.
이번에는 설계만 제안하고 코드·설치·.github 파일 생성은 하지 마.
```

Canvas의 그림만 검사하면 키 입력 연결 오류를 놓칠 수 있습니다.
반대로 브라우저에서 자연스럽게 발생하기 어려운 승패 경계는 제어 가능한 모델 시간으로 확인합니다.
두 검사를 나누되 둘 다 같은 실제 게임 규칙을 대상으로 해야 합니다.

## 승인 후 작성

App을 **Interactive**로 바꿉니다.

**모드: Interactive**

```text
검토한 설계를 승인해. TRD.md를 작성해 줘.
전달한 기술 선택 자료와 합의 내용을 확인할 수 없으면 작성 전에 알려 주고 멈춰 줘.
합의한 렌더링·실행·검증·배포 방식과 포트를 명시해 줘.
PRD 수치를 복제하지 말고 연결하고, 적 탄환·피격·목숨 상태의 실제 명령은 구현 시 manifest에서 확정하도록 해.
서버는 시작한 세션이 포트·PID·URL을 관리하며 모르는 프로세스는 종료하지 않게 해.
코드 생성·의존성 설치는 아직 하지 마.
작성 후 기술 선택 표의 각 항목이 TRD의 어느 절에 반영됐는지 알려 줘.
누락·충돌이 있으면 완료로 표시하지 말고 남은 항목을 보고해 줘.
```

초보자가 알아야 할 것은 규칙·화면·검증의 책임입니다.
루프·리스너의 상세 구현은 Copilot이 맡되 중복 실행은 테스트로 방지합니다.
호환되는 Node LTS와 의존성 선택 근거를 짧게 남기면 충분합니다.
설치 명령부터 실행하고 나중에 manifest를 맞추지 않습니다.

## 눈으로 확인

- [ ] PRD의 모든 주요 규칙에 구현 책임과 검증 경로가 있습니다.
- [ ] 기술 선택 자료를 App에 전달했고 실제 TRD의 해당 절과 대조했습니다.
- [ ] PRD의 필수 수치가 확정됐고 TRD가 SVG 대신 Canvas 2D를 명시합니다.
- [ ] 모델 시간 검사와 실제 브라우저 입력 검사가 구분됐습니다.
- [ ] runtime CDN·외부 그림·테스트 치트 전역 API가 없습니다.
- [ ] dev/E2E·preview 포트와 서버 소유권 원칙이 명확합니다.
- [ ] Pages 하위 경로와 dist 전용 빌드 계획이 있습니다.
