# 03-01. 문서의 정합성 점검

**3. 점검 · 문서의 누락·충돌·모호함 수정**

이전: [02-03 기술 설계](02-03-technical-design.md) · [전체 목차](00-overview.md) · 다음: [03-02 설계 승인](03-02-design-approval.md)

## 1. 설명

문서를 각각 읽으면 맞아 보여도 연결해서 읽으면 서로 다른 게임을 설명할 수 있습니다.
이번에는 아이디어 → 요구사항 → 설계의 연결을 점검하고, **문제가 있는 문장만 승인 후 수정**합니다.
검토 보고서는 대화로 받고 별도의 보고서 파일을 만들지 않습니다.
문서 검토가 끝났다는 사실은 아직 만들지 않은 게임이 테스트를 통과했다는 뜻이 아닙니다.

## 2. 시작 상태

- [ ] 루트에 `AGENTS.md`, `ideation.md`, `PRD.md`, `TRD.md`가 있다.
- [ ] 각 문서의 작성 단계에서 참가자가 내용을 승인했다.
- [ ] 자신의 세션·브랜치와 기존 변경을 확인했다.
- [ ] Copilot app의 **Plan** 모드를 선택했다.

미커밋 변경이 있으면 이번 점검의 수정과 구분합니다. 모든 파일을 일괄 되돌리지 않습니다.

## 3. 실행: 근거 있는 점검과 제한된 수정

### 3-1. Plan에서 문서 연결 검토하기

```text
현재 저장소·브랜치·변경 상태를 읽기 전용으로 확인해줘.
AGENTS.md, ideation.md, PRD.md, TRD.md를 읽고 정합성을 검토해줘.
파일 생성·수정, 설치, 구현, 커밋, 푸시는 하지 마.

두 가지 표를 대화에 작성해줘.
1. REQ-01~08 → PRD 수용 기준 → TRD 설계 절 → 예정 검증 방법의 연결 표.
2. 발견 ID → 종류(누락/충돌/모호함/범위 초과) → 근거 파일·절·문장
   → 영향 → 제안 수정 → 구현 전 해결 필요 여부의 발견 표.

특히 다음을 확인해줘.
- Canvas 800×600, 플레이어 40×20/y550, x 0~760, 발사 간격 0.2초.
- 24개 적·10점·최대 240점, 살아 있는 적 하단 y520 이상이면 패배.
- title/playing/won/lost와 상태별 입력, 초기 시작과 완전한 재시작.
- 탄환 하나당 적 하나 제거, 같은 적의 중복 득점 방지.
- 적 반전·하강 수치, 동시 입력·충돌·종료 처리 순서.
- 긴 프레임과 blur 대응, 키 해제, 초 단위 dt와 단 하나의 RAF.
- Node24/ES modules/Vite/Node 테스트/Playwright, 상대 base './'.
- 테스트 명령의 tests/*.test.js 선택자와 E2E 서버 관리.
- 외부 런타임 의존성 없음, dist만 배포, PR 검사는 배포와 구분.
- CHG-01 일시정지가 최초 PRD의 활성 요구사항에 섞이지 않았는지.

판정은 충족/보완 필요/미확인으로 하고 근거를 함께 적어줘.
계획된 검증과 실제 수행 결과를 구분하고 코드의 실행 성공을 추정하지 마.
문서끼리 충돌하면 구현 편의로 PRD를 바꾸지 말고 내가 결정할 선택지를 제시해줘.
문제가 없으면 억지 수정 대신 '수정 없음'이라고 설명하고 내 검토를 기다려줘.
```

참가자는 발견 표의 근거 문장을 실제 파일에서 확인합니다.
중요도가 높아 보이는 말보다 **어느 요구사항을 어떻게 잘못 구현할 수 있는지**로 우선순위를 정합니다.
합의가 필요한 경우 아래처럼 선택과 범위를 지정합니다.

```text
발견 표에서 구현 전 해결이 필요한 항목부터 다루자.
PRD의 승인된 규칙을 기준으로 TRD를 맞추는 방향을 선택한다.
이번에 수정할 발견 ID와 파일·절, 변경 전후 문장, 영향받는 REQ를 보여줘.
추가 기능이나 코드 수정은 포함하지 마. 아직 파일을 변경하지 마.
```

### 3-2. Interactive에서 선택한 수정만 적용하기

아래 프롬프트의 “방금 제안”이 실제로 검토한 수정 목록인지 확인하고 모드를 바꿉니다.

```text
방금 제안한 수정 목록만 승인한다.
AGENTS.md를 읽고 목록에 명시한 ideation.md/PRD.md/TRD.md의 해당 절만 수정해줘.
목록에 없는 파일과 AGENTS.md는 변경하지 마.
서로 다른 문서에 같은 수치가 있으면 원본 PRD와 참조 관계를 일치시켜줘.
미승인 요구사항 변경이 필요하면 멈추고 알려줘.
설치·구현·커밋·푸시 없이 발견 ID별 변경과 diff를 보여준 뒤 멈춰줘.
```

수정할 문제가 없다면 이 파일 쓰기 단계는 건너뜁니다.

### 예상 결과

- REQ-01~08 연결 표와 근거가 있는 발견 목록.
- 승인된 발견에 대한 문서 수정 또는 “수정 없음” 판단.
- 해결·보류·미확인을 구분한 대화상의 점검 결과.

## 4. 함께 점검·확인

| 점검 항목 | 충족 기준 |
|---|---|
| 연결 | 모든 필수 REQ의 설계와 검증 방법이 존재한다. |
| 근거 | 발견마다 실제 파일·절과 문제가 되는 문장이 있다. |
| 처리 | 수정한 발견의 원인이 사라졌고 다른 문서와 새 충돌이 없다. |
| 범위 | 기능을 추가하거나 수용 기준을 낮춰 문제를 숨기지 않았다. |
| 판단 | 문서 검토 완료와 게임 실행 미확인을 구분한다. |

```text
Plan에서 변경된 문서와 원래 발견 목록을 읽기 전용으로 재검토해줘.
발견 ID별 해결/보류/미확인과 수정된 근거를 보여줘.
REQ-01~08 연결에서 새로 생긴 누락이 있는지도 확인해줘.
보류 항목이 구현을 막는지 설명하고 파일은 수정하지 마.
```

## 5. 보완과 재확인

```text
근거 없이 '문제없음'이라고 한 항목은 미확인으로 바꿔 설명해줘.
충돌하는 두 문장의 파일·절을 나란히 보여주고 하나의 수정 방향을 제안해줘.
필수 요구사항을 삭제하는 해결은 피하고, 실제 수정은 내 승인까지 기다려줘.
```

추가 수정은 다시 Plan 제안 → 참가자 선택 → Interactive 반영 → 재점검 순서로 진행합니다.
예상하지 않은 파일이 바뀌었다면 작업을 멈추고 변경 출처를 확인합니다.

## 6. 완료 승인

- [ ] 구현을 막는 누락·충돌·모호함을 해결했다.
- [ ] 보류 항목의 이유와 영향, 다음 확인 시점을 이해했다.
- [ ] 참가자가 문서 변경과 재점검 결과를 확인했다.

```text
문서 정합성 점검 결과를 승인한다.
실제로 수정하고 내가 검토한 문서만 경로를 확인해 커밋해줘.
메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고,
본문에 03-01 단계 ID, 변경 내용과 이유, 재검토 결과와 미확인 범위를 적어줘.
수정이 없으면 빈 커밋을 만들지 마. 결과와 남은 보류 사항을 알려줘.
푸시·구현·다음 단계는 진행하지 마.
```
