# 07-05. 재배포·확인·회고

**7. 개선 사이클 · 개선 버전 공개와 마무리**

이전: [07-04 변경·회귀 검증](07-04-change-and-regression-testing.md) · [전체 목차](00-overview.md)

## 1. 설명

최초 배포와 같은 검토 경로로 개선 버전을 공개합니다.
작은 변경이라고 검증·PR·병합 승인을 생략하지 않습니다.
**요청 → 문서 → 구현 → 테스트 → 배포 증거**가 이어졌는지 마지막으로 확인합니다.
실습 종료는 기능 개수가 아니라 변경 이유와 검증 근거를 설명할 수 있는 상태입니다.

## 2. 시작 상태

- [ ] CHG-01과 REQ-01~08의 필수 로컬 검증이 통과했다.
- [ ] 개선 브랜치의 승인된 문서·코드·테스트가 로컬 커밋되었다.
- [ ] 최초 배포 SHA·URL과 개선 전 결과를 보존했다.
- [ ] Pages Source·환경의 `main` 제한과 워크플로가 유지되어 있다.
- [ ] **Plan** 모드에서 공개할 diff와 원격 대상을 확인한다.

## 3. 실행: 개선 PR과 배포

```text
개선 버전 공개 전 읽기 전용 점검을 해줘.
저장소, 개선 브랜치, main과의 차이, 미커밋 파일, 로컬 검증 결과를 확인해줘.
CHG-01 관련 변경과 기존 REQ-01~08 회귀 결과를 PR 요약으로 제안해줘.
최초 배포 기록 등 필요한 문서 커밋이 빠지지 않았는지도 확인해줘.
푸시·PR·병합·파일 변경은 하지 말고 공개 승인 대상을 보여줘.
```

대상을 확인하고 **Interactive**로 전환합니다.

```text
방금 확인한 개선 브랜치의 승인 커밋을 해당 Public 저장소에 푸시하도록 허용한다.
main을 대상으로 개선 PR을 생성해줘. 필요한 git/gh 사용은 이 범위에서 허용한다.
CHG-01 요청·설계·구현·검증 연결과 실제 테스트 결과를 본문에 요약해줘.
강제 푸시·main 직접 푸시·병합은 하지 마.
PR URL과 CI 결과를 보여주고 검토를 기다려줘.
```

PR에서 파일 diff와 변경 이유, 검사 결과를 확인합니다.
PR에서는 deploy가 건너뛰어져야 하고 `main`은 아직 최초 배포 상태입니다.
새 커밋이나 리뷰 수정이 생겼다면 마지막 head를 다시 확인합니다.

```text
방금 검토한 개선 PR과 최종 head 커밋의 main 병합을 승인한다.
검사 실패·대기·새 변경·미해결 리뷰가 있으면 멈추고 알려줘.
보호 규칙을 우회하지 말고 병합 후 실제 main Actions 실행 URL을 알려줘.
build와 deploy 결과, 배포 SHA와 실제 page_url을 확인해 보고해줘.
병합 커밋 메시지도 구체적인 한국어 제목·본문으로 작성하고,
단계 ID 07-05와 CHG-01, 변경 내용·이유, 검증 결과와 미확인 범위를 적어줘.
공개 사이트 동작은 별도 검증 전까지 미확인으로 남기고 기다려줘.
```

직접 GitHub 웹에서 병합해도 됩니다. 두 경로를 중복 실행하지 않습니다.
환경 승인 대기가 있으면 기존 승인 절차를 따르고 규칙을 없애지 않습니다.

## 4. 함께 점검·확인: 공개 버전과 기록

Actions의 배포 SHA가 개선 버전인지 확인하고 실제 반환된 URL을 새 창에서 엽니다.
같은 URL을 사용해도 배포 내용은 달라졌으므로 최초 확인 기록을 재사용하지 않습니다.

| 확인 | 공개 사이트의 기대 결과 |
|---|---|
| 정적 전달 | 저장소 하위 경로에서 새로고침, JS·CSS 404와 Console 오류 없음 |
| 변경 동작 | 시작 후 P로 정지, 안내 표시, P로 재개 |
| 시간 보존 | 오래 정지해도 위치·탄환·쿨다운 점프 없음 |
| 입력 경계 | 반복 P 무시, 이동·발사 키 잔류 없음, blur 후 입력 해제 |
| 상태 경계 | title/won/lost에서 P 무시, 종료 후 R/버튼 정상 |
| 기존 기능 | 시작·이동·발사·적·점수·승패·재시작 유지 |

REQ-01~08의 상세 절차는 `TEST_PLAN.md`의 공개 확인 항목을 따라 수행합니다.
브라우저 관찰만으로 내부 쿨다운 정밀도나 단일 RAF를 검증했다고 주장하지 않습니다.
해당 근거는 07-04의 자동 테스트·코드 검토와 함께 연결합니다.

```text
확인한 개선 배포의 실행 URL, SHA, 실제 공개 URL과 브라우저 확인 결과를 정리해줘.
내 수동 관찰과 도구 검증 결과를 구분하고 미확인 항목은 그대로 남겨줘.
TEST_RESULTS.md에 개선 배포 결과를 추가하는 것을 승인한다.
최초 배포 결과를 보존하고 CHANGE_REQUEST.md에는 검증된 완료 상태만 반영해줘.
승인한 구현 계획의 완료 상태도 실제 결과에 맞춰 정리해줘.
ideation.md와 AGENTS.md는 책임 변화가 없다면 수정하지 마.
코드 수정·커밋·푸시는 하지 말고 문서 diff를 보여줘.
```

### 결과 기록을 원격에도 남기기

배포를 본 뒤 작성한 기록은 방금 배포된 SHA에 포함될 수 없습니다.
코드 배포 SHA와 이후 문서 기록 커밋을 구분해서 기록합니다.
기록 diff 승인 후 로컬 커밋을 만들고, 이를 `main`에 남기려면 별도 승인이 필요합니다.

```text
검토한 최종 결과 문서만 구체적인 한국어 제목과 본문으로 로컬 커밋해줘.
제목 예시: '07-05: 일시정지 개선 버전의 공개 배포 검증과 개발 사이클 회고 기록'
본문에 단계 ID 07-05와 CHG-01, 변경 내용·이유, 실제 배포 SHA와 검증 결과를 적어줘.
미확인 범위도 명시하고 아직 푸시하지 마.
이 문서 커밋을 최신 main 기반 기록 브랜치에 보존할 안전한 계획을 제시해줘.
병합된 개선 브랜치 이력을 통째로 재적용하거나 reset·강제 푸시하지 마.
```

계획을 승인한 뒤 fetch·기록 브랜치 준비·문서 커밋 보존을 요청합니다.
그 후 기록 브랜치 푸시·PR 생성, 최종 diff 검토·병합도 각각 승인합니다.
후속 병합 메시지도 한국어 제목·본문에 07-05, 변경 내용·이유, 검증·미확인 범위를 담습니다.
워크플로는 문서만 바뀐 `main` push에서도 재검증·재배포합니다.
이 경우 코드 변경이 없는지, 검사와 배포가 성공했는지 확인하고 공개 URL을 다시 엽니다.
동일 코드의 문서 후속 배포마다 또 다른 기록 PR을 만드는 순환은 필요하지 않습니다.

### 예상 결과

개선 PR과 실제 배포 증거, CHG-01 완료 근거, 보존된 최초 결과가 남습니다.
원격 기록 PR까지 병합했는지 로컬에만 기록했는지도 구분해 보고합니다.

## 5. 보완과 재확인

```text
개선 공개 확인에서 문제가 발견됐다. CHG-01 완료 처리를 보류해줘.
실제 SHA·워크플로 단계·브라우저 증상으로 코드/배포/캐시 문제를 구분해줘.
최소 수정과 회귀 검증 계획 또는 직전 정상 버전 복구안을 제시해줘.
내 승인 없이 되돌리기·푸시·병합·설정 변경은 하지 마.
```

복구가 필요하면 검토 가능한 revert PR을 우선 고려하고 정상 이력을 보존합니다.
복구도 테스트·병합·실제 URL 확인까지 해야 완료입니다.
실패 상태를 성공으로 바꾸거나 최초 결과로 대체하지 않습니다.

## 6. 완료 승인과 회고

- [ ] 개선 버전 배포와 실제 URL을 확인했다.
- [ ] CHG-01 및 기존 요구사항의 증거를 찾을 수 있다.
- [ ] 필요한 문서만 수정했고 미수정 이유를 설명할 수 있다.
- [ ] 원격에 반영된 기록과 로컬에 남은 기록을 구분했다.

```text
개선 사이클의 실제 완료 범위와 결과를 승인한다.
요청이 어떤 문서·코드·테스트·배포 증거로 이어졌는지 최종 요약해줘.
가장 도움이 된 수용 기준, 발견한 회귀 위험, 다음에 개선할 작업 방식을 정리해줘.
확인하지 않은 내용은 남은 과제로 표시하고 추가 기능 구현은 시작하지 마.
이 세션에서 시작한 개발 서버가 남았다면 해당 프로세스만 종료해줘.
추가 커밋·푸시·외부 공유 없이 실습을 마무리해줘.
```
