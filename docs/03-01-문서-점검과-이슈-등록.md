# 03-01. 문서 점검과 이슈 등록

[이전](02-03-기술-설계.md) · [전체 목차](00-전체-실습-안내.md) · [다음: 첫 게임 구현](04-01-첫-게임-구현.md)

## 이번 실습

승인한 문서를 **문서 PR로 main에 먼저 병합**한 뒤 기본 게임 이슈를 만듭니다.
이 순서가 있어야 main에서 시작하는 이슈 세션도 설계를 읽을 수 있습니다.
문서마다 이슈를 만들거나 승인 기록 파일을 여러 개 만들지 않습니다.

## 시작 전

- 문서 세션에 `AGENTS.md`, `ideation.md`, `PRD.md`, `TRD.md`가 있습니다.
- 현재 브랜치는 main과 공통 이력이 있는 문서 브랜치입니다.
- App **Plan**에서 문서 정합성과 공개 범위를 확인합니다.

## 먼저 문서 검토

```text
네 개발 문서의 누락·충돌·과도한 중복을 점검해 줘.
우주 방어의 기본 범위와 수용 기준이 일치하는지 확인해 줘.
카드·에셋 출처와 파일 사양·표시/충돌 경계가 새 구현 세션에도 전달되는지 확인해 줘.
AGENTS가 이후 코드 작업을 막지 않는지, 비밀·사용자 작업 보호가 있는지 봐 줘.
필요한 최소 수정과 main 대상 문서 PR의 변경 범위를 제안해 줘.
아직 코드·이슈·추가 설정 파일을 만들거나 원격에 올리지 마.
```

App **Interactive**로 전환해 필요한 수정만 실행하고 diff를 확인합니다.

```text
확인한 문서 보완을 실행하고 변경을 보여 줘.
검토된 문서만 한국어 커밋으로 남기고 원격 문서 브랜치에 푸시해 줘.
base가 main인 문서 PR을 만들고 링크를 알려 줘. 병합 전에는 멈춰 줘.
```

App의 PR 화면 또는 GitHub 웹에서 base·파일·비밀 유무를 확인합니다.
사람이 승인해 병합한 뒤 GitHub main에서 네 문서가 실제 보이는지 확인합니다.
검사나 보호 규칙이 있다면 기다립니다. 직접 main 덮어쓰기는 대안이 아닙니다.

## 그다음 기본 게임 이슈

```text
문서 PR이 병합됐고 원격 main에 네 문서가 있는지 먼저 확인해 줘.
확인되면 '우주 방어 기본 게임' 이슈 하나를 만들어 줘.
본문은 목표·범위·완료 점검·main의 관련 문서 링크로 간단히 구성해 줘.
M1 시작/이동/발사, M2 적/충돌/점수/승패/재시작,
M3 App 설정/README/로컬 검증을 같은 이슈의 작업으로 넣어 줘.
점수 카드·고정 비행체·이미지 로딩 오류·출처 기록도 완료 점검에 포함해 줘.
배포는 다음 이슈에서 진행한다고 명시하고 template 파일은 만들지 마.
```

실제 이슈 생성 결과의 링크와 번호를 확인합니다.
App **My work → 해당 issue → New session**으로 기본 게임 세션을 엽니다.
선택된 base는 문서가 병합된 **최신 main**이어야 합니다.
예시 기능 브랜치는 `feature-basic-game`이며 App이 접두사를 붙일 수 있습니다.
세션이 자동 시작되면 첫 요청에서 구현 전에 base·문서 확인 후 멈추게 합니다.
M1/M2/M3는 앞으로 **이 한 이슈·한 세션**에서 진행합니다.

## 눈으로 확인

- [ ] 문서 PR이 병합됐고 원격 main에서 네 파일을 볼 수 있습니다.
- [ ] 기본 게임 이슈의 링크가 main 문서를 가리킵니다.
- [ ] 새 세션의 선택 base·현재 브랜치·문서 내용이 맞습니다.
- [ ] M1~M3는 같은 이슈이며 별도의 미세 이슈를 만들지 않았습니다.
- [ ] 배포 완료나 게임 구현 완료를 아직 주장하지 않았습니다.

## 필요할 때만 보완

```text
이슈 세션의 base와 현재 문서가 최신 main에 해당하는지 다시 확인해 줘.
오래된 세션이면 작업을 보존하고 App에서 올바른 새 세션을 여는 방법을 알려 줘.
강제 전환·브랜치 이름 변경·강제 푸시는 하지 마.
```

## 완료

설계는 원격 main에, 구현 요청은 이슈에 보존됐습니다.
새 기본 게임 세션에서 04-01을 시작합니다.
