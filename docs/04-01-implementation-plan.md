# 04-01. 작은 구현 작업으로 계획 나누기

**4. 설계 구현 · `IMPLEMENTATION_PLAN.md` 작성**

이전: [03-02 설계 승인](03-02-design-approval.md) · [전체 목차](00-overview.md) · 다음: [04-02 첫 플레이](04-02-first-playable.md)

## 1. 설명

구현 계획은 설계를 반복하는 문서가 아니라 **무엇부터 바꾸고 어떻게 완료를 확인할지** 정하는 순서표입니다.
한 번의 요청으로 전체 게임을 만들지 않습니다. 첫 조작 가능한 화면, 적·충돌, 종료·재시작을 나눕니다.
각 작업은 REQ, 변경 파일, 의존 작업, 확인 방법, 참가자 승인 지점을 갖습니다.

이번 산출물은 저장소 루트의 `IMPLEMENTATION_PLAN.md` 하나입니다.
`TEST_PLAN.md`와 `TEST_RESULTS.md`는 05단계에서 만들며, 여기서는 예정 검증만 기록합니다.

## 2. 시작 상태

- [ ] `AGENTS.md`, `ideation.md`, `PRD.md`, `TRD.md`가 승인된 상태다.
- [ ] 구현 전 문서 점검이 끝났고 작업 세션·브랜치를 확인했다.
- [ ] 아직 게임 코드와 패키지 설정을 생성하지 않았다.
- [ ] Copilot app에서 **Plan** 모드를 선택했다.

## 3. 실행: 작업의 순서와 완료 조건 정하기

### 3-1. Plan에서 계획 받기

```text
AGENTS.md, ideation.md, PRD.md, TRD.md를 읽고 구현 계획을 제안해줘.
현재 파일·브랜치·기존 변경을 읽기 전용으로 확인해줘.
아직 파일 변경·설치·구현·테스트 실행·커밋·푸시는 하지 마.

작업 ID, 목표, REQ, 의존 작업, 변경 파일, 검증 명령/수동 절차,
완료 조건, 참가자 승인 지점을 가진 작은 작업 표를 만들어줘.
공통 작업 분할은 다음과 같다.
M1: REQ-01/02/03과 REQ-08의 로컬 실행 부분.
  title→playing, 버튼·키보드 시작, 플레이어 이동/경계, 탄환/발사 간격,
  Vite 설정·DOM 표시·단일 RAF·관련 순수 테스트·최소 브라우저 테스트.
  적·충돌·승패·재시작은 아직 구현하지 않으며 전체 요구사항 완료로 표시하지 않는다.
M2: REQ-04/05. 적 편대 이동·하강, 충돌·탄환 소모·점수·중복 방지와 테스트.
M3: REQ-06/07, REQ-08 로컬 통합. 승패·정지·완전한 재시작,
  종료 UI·입력 제한, 기존 기능 회귀 확인과 빌드.
M2와 M3는 같은 안내서에서 다루지만 각각 별도 승인·실행·검토한다.
단계 05: TEST_PLAN.md 작성, 전 요구사항 검증과 TEST_RESULTS.md 기록.
단계 06: PR 검사·main 병합·Actions/Pages 배포. 현재 작업 범위에 포함하지 않는다.

파일 경로는 TRD의 index.html, src/game.js, src/main.js, src/styles.css,
tests/game.test.js, e2e/game.spec.js, playwright.config.js, vite.config.js,
package.json, package-lock.json, .gitignore를 사용한다.
src/game.js는 DOM 없는 순수 규칙이고 테스트는 명시적인 dt로 결정적이어야 한다.
운영 window 치트나 테스트용 즉시 승리 기능은 금지한다.

의존성은 manifest 작성 후 최초 npm install로 lockfile을 만들고 이후 npm ci를 쓴다.
Node24와 ES modules, scripts dev/build/preview/test/test:e2e를 유지한다.
test는 node --test tests/*.test.js로 Node가 e2e를 탐색하지 않게 한다.
설치된 Playwright 의존성 뒤에만 npx playwright install chromium을 실행한다.
E2E webServer는 127.0.0.1의 승인 포트 서버를 직접 관리하고 종료한다.
단계별 명령 실행 허가와 서버의 실행·종료 책임도 계획에 포함해줘.
필요하지 않은 도구·Plugin·게임 엔진·런타임 CDN은 추가하지 않는다.

계획 상태는 미착수/진행 중/완료/차단으로 하되 전부 미착수로 시작한다.
예정 명령을 실행 성공처럼 적지 마. CHG-01 일시정지는 이번 구현에서 제외한다.
전체 계획을 자동 실행하지 말고 대화의 계획 검토에서 멈춰줘.
```

작업 한 칸의 완료 조건이 “잘 작동함”이면 충분하지 않습니다.
예를 들어 M1은 “title에서는 이동하지 않음, 시작 후 x가 0~760, 0.2초 전 추가 발사 없음”으로 나눕니다.
M3가 완료되어도 공개 URL 확인은 아직 미확인입니다.

### 3-2. Interactive에서 계획만 저장하기

```text
방금 검토한 작업 분할과 완료 조건을 승인한다. 이는 구현 실행 승인이 아니다.
AGENTS.md를 읽고 루트 IMPLEMENTATION_PLAN.md만 작성해줘.
작업 ID와 REQ 연결, 의존성, 변경 파일, 검증, 중단·승인 지점을 기록해줘.
모든 구현 작업은 미착수로 두고 차단 요인이 있다면 구분해줘.
코드·설정·다른 문서 생성, 설치, 테스트 실행, 커밋, 푸시는 하지 마.
diff와 첫 작업 M1의 예정 범위만 보여준 뒤 멈춰줘.
```

### 예상 결과

- M1 → M2 → M3의 의존성이 있는 `IMPLEMENTATION_PLAN.md`.
- 각 작업에서 검토할 파일과 요구사항별 완료 조건.
- 구현, 전체 QA, 공개 배포를 구분한 계획.

## 4. 함께 점검·확인

| 점검 항목 | 충족 기준 |
|---|---|
| 작업 크기 | 한 작업을 실행한 뒤 참가자가 직접 조작하고 설명할 수 있다. |
| 연결 | REQ-01~08이 누락되지 않고 담당 작업이 있다. |
| 의존성 | 적이 생기기 전 충돌·승패 완료를 선언하지 않는다. |
| 검증 | 순수 규칙은 결정적 테스트, 사용자 흐름은 실제 브라우저 절차가 있다. |
| 완료 범위 | REQ-08의 공개 배포 확인은 06단계로 남긴다. |
| 승인 | M1 승인만으로 M2/M3가 자동 실행되지 않는다. |

```text
Plan에서 IMPLEMENTATION_PLAN.md를 PRD/TRD와 읽기 전용으로 대조해줘.
누락 REQ, 너무 큰 작업, 검증 없는 완료 조건, 의존성 역전을 찾아줘.
충족/보완 필요/미확인과 근거를 보여주고 실제 작업은 시작하지 마.
```

## 5. 보완과 재확인

```text
한 작업에 전체 게임 생성과 배포가 묶여 있어.
M1의 조작 가능한 화면, M2의 적·충돌, M3의 종료·재시작으로 나눠줘.
각각 독립 검증과 참가자 승인 지점을 넣은 수정안을 Plan에서 보여줘.
REQ를 삭제하거나 구현을 먼저 시작하지 마.
```

승인 후 Interactive에서 `IMPLEMENTATION_PLAN.md`만 수정하고 작업 표를 다시 읽습니다.
시간이 부족하다고 테스트나 승인 지점을 제거하지 말고, 작업을 더 작게 나눕니다.

## 6. 완료 승인

- [ ] 참가자가 첫 작업의 변경 파일과 완료 조건을 설명할 수 있다.
- [ ] 모든 필수 REQ가 계획에 연결되고 아직 구현 전으로 표시되어 있다.
- [ ] 계획 파일 이외의 변경·설치·실행이 없다.

```text
구현 계획 문서를 승인한다. 검토한 IMPLEMENTATION_PLAN.md만 커밋해줘.
메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고,
본문에 04-01 단계 ID, 변경 내용과 이유, 계획 검토 결과와 실행 검증 미수행 범위를 적어줘.
결과를 알려주고 푸시·M1 구현은 하지 마. 다음 실습 요청을 기다려줘.
```
