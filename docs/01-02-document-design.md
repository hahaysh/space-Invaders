# 01-02. 개발 문서의 역할과 구조 정의

**1. 준비 · 개발 문서 정의**

[이전: 작업 환경 준비](01-01-environment-setup.md) · [전체 목차](00-overview.md) · [다음: 작업 지침 작성](01-03-agent-instructions.md)

## 1. 설명

Space Invaders를 만들기 전에 **무엇을 어느 문서에 기록할지** 결정합니다.

“게임을 만들어줘”라고 요청하면 빠르게 코드가 나올 수 있지만, 왜 그 기능을 선택했는지, 어떤 동작이 완료 기준인지, 변경할 때 무엇을 확인해야 하는지 놓치기 쉽습니다. 문서는 이런 결정을 다음 작업에서도 사용할 수 있게 해 줍니다.

이번 단계는 문서의 내용을 완성하는 시간이 아닙니다. **문서의 목적·목차·참조 관계·완료 기준을 대화로 정의**하고, 실제 작성은 다음 단계부터 진행합니다.

### 구분할 문서

| 문서 | 답해야 할 질문 | 이번 단계에서 정할 것 |
|---|---|---|
| `AGENTS.md` | 에이전트는 어떤 규칙으로 작업할까? | 작업 범위, 승인, 문서 참조, 검증과 기록 규칙 |
| `ideation.md` | 어떤 게임 경험을 왜 만들까? | 대상 사용자, 아이디어 후보, 선택 이유, 제외 범위 |
| `PRD.md` | 무엇을 만들고 언제 완료로 인정할까? | 요구사항 ID, 우선순위, 수용 기준 |
| `TRD.md` | 요구사항을 어떻게 구현하고 검증할까? | 기술 선택, 구조, 상태 전환, 시간·입력 처리, 테스트·배포 |
| `IMPLEMENTATION_PLAN.md` | 어떤 순서로 작업할까? | 요구사항별 작업, 의존성, 변경 파일, 완료 조건 |
| `TEST_PLAN.md` | 무엇을 어떻게 확인할까? | 요구사항별 자동·수동 테스트와 경계 조건 |
| `TEST_RESULTS.md` | 실제로 무엇을 확인했을까? | 환경, 실행 명령·절차, 실제 결과, 미확인 사항 |

`AGENTS.md`는 프로젝트 작업 지침이며 특정 역할의 Custom agent 정의 파일과 다릅니다. PRD는 제품 요구사항 문서, TRD는 기술 설계 문서입니다. 파일이 존재하는 것만으로 그 내용이 항상 자동 적용된다고 가정하지 않습니다.

예를 들어 “적을 맞히면 점수가 증가한다”는 요구사항은 PRD에, 충돌과 점수 처리 설계는 TRD에, 구현 순서는 구현 계획에, 확인 절차와 실제 결과는 테스트 문서에 연결합니다. 동일한 수치를 여러 곳에 별도로 복제하기보다는 요구사항 ID를 참조합니다.

## 2. 시작 상태

- [ ] 자신의 Public 저장소가 Copilot app 프로젝트에 연결되어 있다.
- [ ] 실습 작업 세션의 저장소·작업 공간·브랜치를 확인했다.
- [ ] 게임 코드와 위 개발 문서가 아직 없는 상태이다.
- [ ] 기존 작업이 있다면 임의로 삭제하지 않고, 새 실습 저장소가 맞는지 먼저 확인한다.
- [ ] Copilot app의 **Plan** 모드를 선택했다.

현재 단계에서는 프로젝트 파일을 만들거나 수정하지 않습니다. 저장소 초기화 과정에서 필요한 최소 Git 메타데이터는 게임 코드나 개발 문서와 구분합니다.

## 3. 실행: 문서 구성 제안받기

Copilot app의 해당 작업 세션에 다음 프롬프트를 입력합니다. 안내서를 참가자 저장소로 복사할 필요는 없습니다.

```text
우리는 GitHub Copilot app으로 Space Invaders 게임을 만드는 실습을 진행한다.
이번 단계의 목표는 개발 문서의 역할과 구조를 정의하는 것이다.

먼저 현재 저장소, 브랜치, 기존 파일 상태를 읽기 전용으로 확인해줘.
예상과 다르게 게임 코드나 개발 문서가 이미 있으면 알려주고 멈춰줘.
파일 생성·수정, 패키지 설치, 커밋, 푸시, 게임 구현은 하지 마.

실습의 공통 경로는 다음과 같다.
- HTML/CSS/JavaScript와 Canvas 2D로 브라우저 게임을 만든다.
- Vite로 개발·빌드하고 Node 내장 테스트와 Playwright로 검증한다.
- GitHub Actions로 GitHub Pages에 배포한다.
- 최초 버전은 시작, 좌우 이동, 발사, 적 편대 이동·하강,
  충돌, 점수, 승리·패배, 재시작을 포함한다.
- 최초 배포 후 일시정지·재개를 추가하는 개선 사이클을 진행한다.
- 상세 수치와 게임 규칙은 이후 PRD에서 결정한다.

다음 문서의 역할과 구조를 제안해줘.
AGENTS.md, ideation.md, PRD.md, TRD.md,
IMPLEMENTATION_PLAN.md, TEST_PLAN.md, TEST_RESULTS.md

각 문서에 대해 다음 항목을 표로 제시해줘.
1. 목적
2. 최소 필수 목차와 각 목차에 작성할 내용
3. 포함하지 않거나 다른 문서를 참조할 내용
4. 작성 시 참조할 문서
5. 완료를 판단하는 기준

요구사항 ID를 설계·구현 작업·테스트와 연결하는 방법도 설명해줘.
테스트 계획과 실제 수행 결과를 구분하고, 수행하지 않은 테스트를
통과로 기록하지 않도록 해줘.

AGENTS.md는 작업 지침이고 Custom agent 정의와는 다름을 설명해줘.
아직 결정되지 않은 명령·수치를 확정 사실로 작성하지 마.
처음에는 최소 지침을 만들고 TRD 확정 후 보완하는 순서를 제안해줘.

마지막에 작성 순서와 결정이 필요한 사항을 요약하고 내 검토를 기다려줘.
아직 문서 본문을 완성하거나 다음 실습을 시작하지 마.
```

### 예상 결과

- 문서별 역할·목차·완료 기준 표.
- 문서 작성 순서와 참조 관계.
- 미결정 사항 목록.
- 프로젝트 파일 변경 없음.

표의 표현이 예시와 달라도 됩니다. 문서의 책임과 연결 관계를 설명할 수 있는지가 중요합니다.

## 4. 함께 점검·확인

먼저 참가자가 제안 표와 app의 변경 내역을 직접 확인합니다.

| 점검 항목 | 충족 기준 |
|---|---|
| 작업 지침 | `AGENTS.md`에 게임 전체 명세를 복제하지 않고 작업·승인·검증 규칙을 둔다. |
| 아이디어와 요구사항 | 후보·선택 이유와 확정된 기능·수용 기준을 구분한다. |
| 요구사항과 설계 | “무엇을 만족해야 하는가”와 “어떻게 구현하는가”를 구분한다. |
| 테스트 계획과 결과 | 확인 방법과 실제 수행 증거를 별도로 기록한다. |
| 연결 관계 | 요구사항 ID를 구현 계획과 테스트에서 참조한다. |
| 실습 규모 | 게임에 필요하지 않은 조직·대규모 서버 운영 문서를 추가하지 않는다. |
| 미결정 사항 | 속도·점수·적 수 등 아직 합의하지 않은 값을 결정 필요로 남긴다. |
| 변경 범위 | 파일 생성·수정·설치·커밋·푸시가 없다. |

그다음 아래 검토 프롬프트를 입력합니다.

```text
방금 제안한 문서 구조를 검토해줘. 아직 파일은 변경하지 마.

문서 역할의 중복, 빠진 책임, 불필요한 복잡성,
미결정 사항을 확정한 부분, 요구사항에서 테스트까지의 연결을 확인해줘.

각 항목을 '충족 / 보완 필요 / 미확인'으로 표시하고
방금 제안의 어떤 부분을 근거로 판단했는지 설명해줘.
문제가 없는 것처럼 추정하지 말고, 확인할 수 없는 내용은 미확인으로 남겨줘.
기존 상태와 비교해 파일 변경이 없는지도 읽기 전용으로 확인해줘.

수정안을 제시하되 실제 파일을 만들지는 말고 내 확인을 기다려줘.
```

AI의 자체 검토만으로 완료하지 않습니다. 참가자가 PRD와 TRD의 차이, 테스트 계획과 결과의 차이를 자기 말로 설명할 수 있는지 확인합니다.

## 5. 보완과 재확인

문제가 있을 때 해당 상황의 프롬프트를 사용합니다.

### 문서가 너무 크거나 중복되는 경우

```text
제안이 이 게임 실습에 비해 복잡해.
지금 합의한 문서 목록은 유지하되 각 문서의 목차를 필요한 최소 수준으로 줄여줘.
중복된 요구사항 본문은 PRD를 기준으로 두고 다른 문서는 ID로 참조하도록 바꿔줘.
삭제하거나 합친 목차와 이유를 설명하고, 파일 변경 없이 수정안을 보여줘.
```

### 아직 합의하지 않은 기능이나 값을 확정한 경우

```text
최초 버전에 없던 기능 또는 아직 합의하지 않은 수치를 확정한 부분을 찾아줘.
해당 내용을 '결정 필요' 또는 '범위 밖'으로 구분해 제안을 수정해줘.
일시정지·재개는 개선 사이클에서 추가하며 최초 버전에 넣지 마.
파일은 변경하지 말고 수정된 항목만 설명해줘.
```

### 예상하지 않은 파일 변경이 발생한 경우

```text
이 단계에서는 파일 변경을 허용하지 않았어. 추가 작업을 멈춰줘.
변경 파일과 변경 내용을 읽기 전용으로 보여주고,
이번 요청으로 생긴 변경인지 기존 사용자 작업인지 구분해줘.
내 승인 없이 삭제·되돌리기·커밋하지 마.
```

변경의 출처가 불명확하면 진행자와 확인합니다. 저장소 전체 초기화나 일괄 되돌리기로 해결하지 않습니다.

## 6. 완료 승인

- [ ] 문서별 목적·최소 목차·참조 문서·완료 기준을 합의했다.
- [ ] 요구사항 → 설계 → 구현 작업 → 테스트의 연결을 설명할 수 있다.
- [ ] 실제 검증하지 않은 내용을 결과로 기록하지 않는 원칙을 이해했다.
- [ ] 미결정 사항을 다음 작성 단계에서 처리하도록 남겼다.
- [ ] 예상하지 않은 프로젝트 파일 변경이 없다.

모두 충족하면 다음 프롬프트를 입력합니다.

```text
이번 단계의 문서 역할과 구조를 승인한다.
합의한 문서별 목적, 최소 목차, 작성 순서, 미결정 사항을
다음 단계에서 참고할 수 있게 대화에 최종 요약해줘.
아직 파일은 생성하지 말고, AGENTS.md 작성도 시작하지 마.
내가 다음 실습 프롬프트를 입력할 때까지 기다려줘.
```

이번 단계의 산출물은 **승인된 대화 요약**입니다. 다음 단계에서 그 내용을 참조해 `AGENTS.md`를 실제로 작성합니다. 세션을 바꾸면 승인 요약을 새 세션에 전달하고 같은 저장소·브랜치인지 확인합니다.

파일 변경이 없으므로 이 단계만을 위한 빈 커밋은 만들지 않습니다.
