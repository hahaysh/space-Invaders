# 05-01. 요구사항별 검증과 실제 결과 기록

**5. 검증 · `TEST_PLAN.md`와 `TEST_RESULTS.md` 작성**

이전: [04-03 핵심 게임](04-03-core-gameplay.md) · [전체 목차](00-overview.md) · 다음: [05-02 수정과 회귀](05-02-fixes-and-regression.md)

## 1. 설명

테스트 계획은 **확인할 방법**, 테스트 결과는 **실제로 확인한 증거**입니다.
자동 테스트가 모두 통과해도 빠진 요구사항, 실제 브라우저 조작, 공개 URL 확인은 별개입니다.
REQ별 검사표 승인 후 실행 결과를 기록합니다. 실패는 바로 수정하지 않고 다음 실습에서 수정안을 승인합니다.

## 2. 시작 상태

- [ ] M1~M3 구현과 작업별 검증을 마쳤고 남은 미확인을 알고 있다.
- [ ] `AGENTS.md`, `PRD.md`, `TRD.md`, `IMPLEMENTATION_PLAN.md`가 현재 코드와 맞는다.
- [ ] 잠금 파일·순수/브라우저 테스트가 있고 E2E 포트에 수동 서버가 남아 있지 않다.
- [ ] Copilot app에서 **Plan** 모드를 선택했다.

## 3. 실행: 계획 작성 → 승인 → 실제 검증

### 3-1. Plan에서 테스트 범위 설계하기

```text
AGENTS.md, PRD.md, TRD.md, IMPLEMENTATION_PLAN.md와 테스트 코드를 읽어줘.
파일 변경·명령 실행·설치·수정·커밋·푸시 없이 TEST_PLAN.md 초안을 제안해줘.
TC ID, REQ ID, 방법(Node/Playwright/수동), 전제 상태·입력·절차,
기대 결과, 현재 테스트 연결, 미구현 검사 여부를 표로 적어줘.

최소 검사는 다음과 같다. 하나의 REQ에 여러 TC를 배정해도 된다.
REQ-01: title에서 버튼/Enter 각각 시작, 점수0, 시작 전 이동·발사 없음.
REQ-02: 좌우/A/D, x0/760 경계, 양 방향 동시 입력, blur 후 키 해제.
REQ-03: 첫 발사, 0.2초 미만/도달 발사 간격, Space 유지, 화면 밖 탄환 제거.
REQ-04: 24개 초기 편대, 수평 이동과 경계 반전·한 번 하강.
REQ-05: 충돌/비충돌, 한 탄환·여러 적, 여러 탄환·한 적, 중복 없이 10점.
REQ-06: 전멸·240점·won, 적 하단 520 직전/도달·lost, 판정 순서, 종료 후 정지.
REQ-07: won/lost 각각 R/버튼 재시작, 모든 판 상태 초기화, 입력·시간 초기화,
  연속 재시작에도 RAF·리스너 중복 없음, playing 중 Enter/R 무시.
REQ-08: 상태·점수·버튼 DOM, 실제 빌드 실행, 상대 에셋 경로,
  외부 런타임 CDN/엔진/에셋 서버 없음.

물리·시간 경계는 명시적 dt로 결정적 순수 테스트를 사용한다.
DOM과 사용자 입력은 실제 브라우저에서 확인한다.
운영 window 치트·테스트용 즉시 승패 조작은 쓰지 않는다.
전체 승패 플레이처럼 긴 흐름은 참가자의 실제 수동 확인 절차를 적어줘.
CHG-01 일시정지는 현재 필수 테스트가 아니다.
공개 Pages URL·배포 권한은 아직 미확인으로 두고 06단계에서 확인한다.
누락 테스트가 있으면 알려주되 지금 코드를 쓰지 말고 내 검토를 기다려줘.
```

검사표를 읽고 각 REQ의 정상·경계·금지 동작이 연결되는지 확인합니다.
검증 방법 자체가 없다면 계획을 먼저 보완합니다. 자동화가 없더라도 재현 가능한 수동 절차는 둘 수 있습니다.

### 3-2. Interactive에서 계획만 저장하기

```text
검토한 테스트 계획을 승인한다. AGENTS.md를 읽고 루트 TEST_PLAN.md만 작성해줘.
자동화가 없는 검사는 수동 절차 또는 미구현 검사로 구분해줘.
다른 파일·코드·테스트 수정과 실행, 설치, 커밋, 푸시는 하지 마.
diff를 보여주고 실제 실행 승인을 기다려줘.
```

파일을 직접 읽고 검사 ID·전제·기대 결과가 빠지지 않았는지 확인한 뒤 실행을 승인합니다.

### 3-3. Interactive에서 검증하고 결과 초안 기록하기

```text
저장된 TEST_PLAN.md의 검증 실행을 승인한다. AGENTS.md를 다시 읽어줘.
현재 브랜치·커밋·미커밋 변경, 운영체제, Node/npm/Playwright 버전을 확인해줘.
잠금 파일 기준 npm ci 후 npm test, npm run test:e2e, npm run build를 실행해줘.
test 스크립트가 node --test tests/*.test.js인지 먼저 확인하고
다르면 임의로 고치지 말고 차단 원인으로 보고해줘.
Chromium이 없다는 실패가 발생할 때만 설치된 Playwright를 사용해
npx playwright install chromium 후 E2E를 다시 실행하고 두 결과를 남겨줘.
E2E 서버는 설정된 127.0.0.1 포트의 webServer로 관리하고 타인 서버를 종료하지 마.
실패한 명령은 실제 출력·종료 상태와 함께 기록하고 테스트나 구현을 수정하지 마.

루트 TEST_RESULTS.md를 새로 작성하거나 기존 기록 뒤 새 실행 회차를 추가해줘.
실행 일시·검증 대상·환경·명령·실제 결과·증거 위치를 기록해줘.
TC별 상태는 통과(pass)/실패(fail)/미확인(unverified)만 사용한다.
실제 assertion이나 관찰 증거를 연결하고 전체 테스트 성공을 모든 TC에 복제하지 마.
실행 못 한 항목은 사유와 후속 확인 방법을 적어줘.
코드·테스트·계획을 고치거나 성공 로그를 만들어내지 마.
diff와 실제 실행 결과를 보여주고 수동 확인 대기에서 멈춰줘. 커밋·푸시는 하지 마.
```

### 3-4. 빌드 결과 직접 확인하기

빌드 성공 후 에이전트에게 아래 명령으로 서버를 실행하고 응답을 확인하도록 요청합니다.

```text
npm run preview -- --host 127.0.0.1 --port 4173 --strictPort
```

이 명령은 app에서 에이전트에게 실행을 요청하는 내용입니다. 서버가 실제 시작된 뒤 알려준 URL을 엽니다.
`TEST_PLAN.md`의 버튼·키보드·실제 승패·재시작 절차를 따라하고, 관찰한 TC와 결과를 대화에 전달합니다.
“TC-…: 패배 후 R을 누르니 0점·적 24개로 시작했다”처럼 증거를 적습니다.
에이전트에게 **전달한 관찰만** `TEST_RESULTS.md`에 반영하도록 요청하고 diff를 다시 읽습니다.

### 예상 결과

- REQ-01~08과 검증 절차를 연결한 `TEST_PLAN.md`.
- 실제 명령·수동 관찰과 다음 단계의 결함·미확인을 구분한 `TEST_RESULTS.md`.

## 4. 함께 점검·확인

| 점검 항목 | 충족 기준 |
|---|---|
| 대응 | 모든 TC에 REQ와 기대 결과가 연결된다. |
| 증거 | 통과 판정마다 실제 테스트 또는 참가자 관찰 근거가 있다. |
| 환경 | 어떤 커밋과 미커밋 변경을 검사했는지 식별할 수 있다. |
| 미확인 | 못 실행한 항목·공개 URL을 통과로 기록하지 않았다. |
| 공개 안전 | 토큰·개인정보·로컬 사용자 경로가 담긴 원문 로그를 무심코 커밋하지 않는다. |

## 5. 보완과 재확인

```text
Plan에서 TEST_PLAN.md와 TEST_RESULTS.md를 읽기 전용으로 검토해줘.
증거 없는 통과, TC 누락, 계획과 실제 결과 혼동을 찾아 수정안을 보여줘.
기능 실패는 고치지 말고 재현 절차·기대/실제 결과·관련 REQ로 정리해줘.
```

승인 후 Interactive에서 필요한 테스트 문서만 보완합니다. 기능·자동화 수정은 05-02로 넘깁니다.
검증이 실패한 상태도 정확히 기록하면 이 단계의 기록 목적은 달성합니다. 배포 준비 완료는 아닙니다.

## 6. 완료 승인

- [ ] 참가자가 결과와 증거를 읽고 실패·미확인을 이해했다.
- [ ] 문서 두 개가 저장되었고 실제 수행하지 않은 성공 기록이 없다.
- [ ] 수동 확인용 preview 서버는 이번 작업이 시작한 프로세스만 종료했다.

```text
테스트 계획과 실제 결과 기록을 승인한다. 전체 기능 통과 승인과는 구분한다.
검토한 TEST_PLAN.md와 TEST_RESULTS.md만 커밋해줘. 메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고, 본문에 05-01 단계 ID, 변경 내용과 이유, 실제 검증 결과와 미확인 범위를 적고 커밋 결과를 알려줘.
생성 보고서·개인정보를 포함하거나 푸시하지 마. 결함 수정은 다음 요청을 기다려줘.
```
