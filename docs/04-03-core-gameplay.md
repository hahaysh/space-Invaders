# 04-03. 적·충돌과 종료·재시작 구현

**4. 설계 구현 · M2와 M3를 별도로 승인**

이전: [04-02 첫 플레이](04-02-first-playable.md) · [전체 목차](00-overview.md) · 다음: [05-01 요구사항 테스트](05-01-requirements-testing.md)

## 1. 설명

적 편대·점수 다음 승패·재시작을 추가합니다. **M2 확인 전에 M3를 실행하지 않습니다.**
첫 버전이므로 일시정지, 목숨, 적 탄환, 사운드, 여러 웨이브는 추가하지 않습니다.

## 2. 시작 상태

- [ ] M1을 참가자가 확인했고 구현 계획에 상태·근거가 있다.
- [ ] 의존성·Chromium·잠금 파일이 준비되어 있고 PRD의 적 수치·종료 우선순위가 확정되었다.
- [ ] 세션·브랜치를 확인하고 E2E 포트의 수동 개발 서버는 종료했다.
- [ ] Copilot app에서 **Plan** 모드를 선택했다.

## 3. 실행: 두 작업을 나누어 완성하기

### 3-1. Plan → Interactive: M2 적·충돌·점수

```text
AGENTS.md, PRD.md, TRD.md, IMPLEMENTATION_PLAN.md와 M1 코드를 읽어줘.
M2(REQ-04/05)만 제안해줘. 적 편대 이동·하강, 탄환 충돌·점수의
변경 파일·처리 순서·경계 테스트·직접 확인 절차를 보여줘.
24개 적과 10점, 한 탄환당 최대 한 적 제거, 중복 득점 방지를 포함해줘.
M3 승패·재시작이나 일시정지는 아직 구현하지 마.
파일 변경·설치·실행·커밋·푸시 없이 승인을 기다려줘.
```

계획이 맞으면 Interactive에서 요청합니다.

```text
M2 계획을 승인한다. AGENTS.md를 읽고 승인한 M2 파일만 수정해줘.
PRD의 수치와 TRD의 순수 규칙/브라우저 책임 분리를 유지해줘.
살아 있는 적의 경계로 편대를 반전·하강시키고 프레임마다 중복 하강하지 않게 해줘.
탄환 하나가 겹친 적 여러 개를 동시에 제거하지 않고 즉시 소모되게 해줘.
이미 제거한 적은 다른 탄환의 점수 계산에 다시 사용하지 마.
적 이동/경계/하강, 적 하나와 여러 탄환, 탄환 하나와 여러 적,
충돌 없음·경계 접촉·최대 점수를 명시적인 dt와 상태로 순수 테스트해줘.
tests/game.test.js는 순수 API를 사용하고 운영 window 치트를 추가하지 마.
npm test, npm run test:e2e, npm run build로 기존 M1도 확인해줘.
실행 증거와 diff를 보여주고 M2 참가자 확인 대기에서 멈춰줘.
추가 설치·커밋·푸시·M3 진행은 하지 마.
```

### 3-2. M2 직접 확인과 승인

04-02와 같은 개발 서버 실행·응답 확인을 요청한 뒤 적 3행×8열, 반전·하강, 적 하나당 10점을 확인합니다.
M2에는 아직 종료 동작이 없으므로 적 전멸 뒤 승리 화면이 없는 것을 새 결함으로 처리하지 않습니다.

```text
M2의 적·충돌·점수를 직접 확인했다. 확인한 범위의 완료를 승인한다.
IMPLEMENTATION_PLAN.md의 M2 상태와 실제 근거를 갱신하고 diff를 보여줘.
미확인은 남겨두고 M3·커밋·푸시는 하지 마.
이번 작업에서 시작한 개발 서버만 종료해줘.
```

계획 diff 검토 후 “M2의 승인된 변경만 커밋하고 푸시하지 마. 메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고, 본문에 04-03/M2 단계 ID, 변경 내용과 이유, 실제 검증 결과와 미확인 범위를 적어줘”라고 요청합니다.

### 3-3. Plan → Interactive: M3 승패·재시작

Plan으로 돌아가 다음 작업만 제안받습니다.
```text
승인된 문서와 M2 코드를 읽고 M3(REQ-06/07, REQ-08 로컬 통합)를 계획해줘.
승리/패배 판정 순서, 종료 후 입력·시뮬레이션 정지, DOM 상태·버튼,
R/버튼 재시작과 모든 판 상태 초기화의 변경 파일·테스트를 제안해줘.
승패 직전 상태는 순수 테스트에서 구성하고 운영 코드에 치트를 노출하지 마.
실제 브라우저에서 가능한 검사와 별도 수동 확인을 구분해줘.
파일 변경·명령 실행·설치·커밋·푸시 없이 내 승인을 기다려줘.
```

계획 검토 후 Interactive로 전환합니다.
```text
M3 계획을 승인한다. AGENTS.md를 읽고 승인한 M3 파일만 구현해줘.
적 전멸은 won, 살아 있는 적 하단 y>=520은 lost로 하고
PRD에서 승인한 충돌·종료 판정 순서를 유지해줘.
title/won/lost에서는 이동·발사와 시뮬레이션 갱신을 하지 않는다.
won/lost에서만 R 또는 재시작 버튼으로 playing의 새 판을 만든다.
플레이어 위치, 적 24개·방향, 점수0, 빈 탄환, 발사 대기시간,
눌린 키와 이전 프레임 시간을 초기화하고 RAF는 하나만 유지해줘.
종료와 재시작을 반복해도 입력 리스너·루프가 중복되지 않게 해줘.
순수 테스트에 마지막 적 제거/240점, 적 하단 520 직전·도달,
동시 종료 우선순위, 종료 후 갱신 없음, 승리·패배 각각의 재시작,
재시작 후 즉시 발사 가능과 초기 상태 복원을 포함해줘.
브라우저 테스트는 사용자 키·버튼과 접근 가능한 DOM으로 검증해줘.
승패를 치트로 만들지 말고 긴 사용자 흐름은 수동 확인 항목으로 명시해줘.
npm test, npm run test:e2e, npm run build를 실행하고 실제 결과를 보고해줘.
IMPLEMENTATION_PLAN.md는 실제 진척만 갱신하고 참가자 확인 대기로 남겨줘.
diff를 보여준 뒤 멈춰줘. 커밋·푸시·일시정지·배포는 하지 마.
```

### 예상 결과

- 적 전멸 시 240점·승리, 적 하단 y520 도달 시 패배하며 종료 뒤 움직임·득점이 멈춘다.
- 승패 후 R 또는 버튼으로 깨끗한 새 판을 시작한다.
- 각 작업의 테스트 증거가 있고 공개 배포 검증은 아직 남아 있다.

## 4. 함께 점검·확인

개발 서버를 다시 실행·응답 확인한 뒤 실제 게임을 조작합니다.
| 확인 항목 | 기대 결과 |
|---|---|
| 실제 한 판 승리 | 모든 적이 사라지고 240점·won을 표시한다. |
| 발사하지 않고 패배까지 기다리기 | 적 하단이 기준선에 도달하면 lost로 바뀐다. |
| 종료 뒤 좌우·Space | 이동·발사·점수 변화가 없다. |
| 승패 후 각각 R와 버튼 | 초기 위치·적 24개·0점·빈 탄환의 새 판이다. |
| 여러 번 재시작·포커스 전환 | 속도·발사 빈도가 배로 늘지 않고 입력이 붙지 않는다. |
| playing 중 Enter/R | 진행 중인 판이 예고 없이 초기화되지 않는다. |

실제 승리를 확인하지 못하면 **미확인**으로 남겨 05단계에서 이어서 확인합니다. 순수 테스트로 대체하지 않습니다.

## 5. 보완과 재확인

```text
Plan에서 재시작 후 움직임이 빨라지는 증상의 원인을 읽기 전용으로 조사해줘.
단일 RAF·입력 리스너·시간 초기화 경로를 확인하고 최소 수정과 회귀 테스트를 제안해줘.
통과시키려고 PRD나 테스트 기대값을 완화하지 마. 승인 전에는 수정하지 마.
```

승인 후 Interactive에서 해당 수정·테스트만 실행하고 재시작을 여러 번 직접 확인합니다.
E2E 실행 전에는 자신이 시작한 개발 서버만 종료해 포트 충돌을 피합니다.

## 6. 완료 승인

- [ ] M2/M3의 코드·자동 검증을 각각 검토했고 실제 확인과 남은 미확인을 구분했다.
- [ ] 최초 버전에 일시정지나 미승인 기능이 없다.

```text
M3 구현 결과를 승인한다. 실제 확인 근거와 남은 미확인을
IMPLEMENTATION_PLAN.md에 반영하고 diff를 보여줘. 커밋·푸시는 아직 하지 마.
```

diff 검토 후 “M3의 승인된 변경만 커밋해줘. 메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고, 본문에 04-03/M3 단계 ID, 변경 내용과 이유, 실제 검증 결과와 미확인 범위를 적어줘. 푸시·QA·배포는 시작하지 마”라고 요청합니다.
수동 개발 서버는 이번 작업이 시작한 프로세스만 식별해 종료하도록 요청합니다.
