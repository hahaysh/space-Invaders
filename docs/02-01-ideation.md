# 02-01. 아이디어 논의와 선택 기록

**2. 게임 설계 · `ideation.md` 작성**

이전: [01-03 에이전트 지침](01-03-agent-instructions.md) · [전체 목차](00-overview.md) · 다음: [02-02 제품 요구사항](02-02-product-requirements.md)

## 1. 설명

아이디어 문서는 게임의 기능 목록보다 **누가 어떤 경험을 하고, 왜 이 범위를 선택했는지** 설명합니다.
여러 후보를 비교하되, 짧은 실습 안에 직접 만들고 확인할 수 있는 하나를 선택합니다.
이번 산출물은 참가자 저장소 루트의 `ideation.md`입니다. 안내서나 참고 샘플을 복사하지 않습니다.

공통 경로는 브라우저에서 좌우로 이동하며 적 편대를 맞히는 한 화면 게임입니다.
색상·도형·제목은 자유롭게 선택할 수 있습니다. 규칙을 바꾸는 변형도 요청할 수 있지만,
요구사항·설계·테스트와 이후 안내를 함께 조정해야 한다는 영향을 먼저 확인합니다.

## 2. 시작 상태

- [ ] 자신의 Public 저장소와 작업 세션·브랜치를 확인했다.
- [ ] 01-02에서 문서 역할을 합의했고 루트에 최소 `AGENTS.md`를 작성했다.
- [ ] 게임 코드와 `ideation.md`는 아직 없다. 기존 파일이 있으면 덮어쓰지 않고 비교한다.
- [ ] Copilot app에서 **Plan** 모드를 선택했다.

모드만으로 행동을 제한한다고 가정하지 않습니다. 프롬프트에도 읽기 전용 범위를 명시합니다.

## 3. 실행: 후보 비교 후 문서 작성

### 3-1. Plan에서 논의하기

```text
현재 저장소·브랜치·기존 파일을 읽기 전용으로 확인하고 AGENTS.md를 읽어줘.
합의한 문서 구조를 참고해 Space Invaders의 아이디어를 논의하자.
파일 생성·수정, 설치, 구현, 커밋, 푸시는 하지 마.

대상은 키보드로 짧게 플레이할 브라우저 게임 초보자다.
공통 실습 경로와 시각적 테마 변형 2개를 표로 비교해줘.
대상 사용자, 핵심 재미, 한 판의 흐름, 실습 난이도, 제외 범위를 적어줘.
외부 캐릭터·이미지·음원 대신 직접 그린 도형과 자체 스타일을 사용한다.

공통 경로는 800×600 Canvas, 좌우 또는 A/D 이동, Space 발사다.
Enter 또는 시작 버튼으로 시작하고 승패 뒤 R 또는 버튼으로 재시작한다.
적은 3행×8열, 한 적당 10점, 단일 웨이브이며 모두 제거하면 승리한다.
적 하단이 y=520에 도달하면 패배한다.
최초 버전은 목숨·적 탄환·사운드·모바일·온라인 순위·일시정지가 없다.
일시정지는 최초 배포 뒤 개선 요청 CHG-01에서 다룬다.

다른 규칙을 제안한다면 기본 경로와 달라지는 부분 및 후속 문서·테스트 영향을 밝혀줘.
아직 후보를 내 대신 확정하지 마.
마지막에 내가 선택할 후보와 결정해야 할 질문을 제시하고 기다려줘.
```

후보를 읽고 참가자가 제목·테마·대상을 선택합니다. 결정은 다음처럼 답할 수 있습니다.

```text
공통 게임 규칙을 유지하는 기본 후보를 선택한다.
제목은 Orbit Defender, 테마는 어두운 우주와 밝은 도형으로 정한다.
선택 이유는 작은 범위에서 문서·구현·테스트·배포를 모두 경험하기 위해서다.
이 선택을 반영한 ideation.md 본문 초안을 대화에 보여줘.
문제, 대상 사용자, 핵심 경험, 후보 비교, 선택 이유, 포함·제외 범위,
다음 PRD에서 확정할 수치와 미결정 사항을 포함해줘. 파일은 아직 쓰지 마.
```

### 3-2. 승인한 내용만 Interactive에서 기록하기

초안이 맞으면 **Interactive** 모드로 바꾸고 입력합니다.

```text
방금 검토한 아이디어 초안을 승인한다.
AGENTS.md를 다시 읽고 저장소 루트에 ideation.md만 작성해줘.
선택한 후보와 이유, 공통 규칙, 제외 범위, PRD로 넘길 결정 사항을 기록해줘.
세부 구현 방법이나 아직 수행하지 않은 테스트 결과는 넣지 마.
이미 파일이 있다면 차이를 먼저 보여주고 덮어쓰지 마.
다른 문서·코드 생성, 설치, 커밋, 푸시는 하지 말고 diff를 보여준 뒤 멈춰줘.
```

### 예상 결과

- 후보 비교에서 선택으로 이어지는 근거가 담긴 `ideation.md` 하나.
- 최초 버전과 후속 개선을 구분한 범위.
- PRD에서 구체화할 이동 속도·적 이동 방식 등의 결정 목록.

## 4. 함께 점검·확인

app에서 파일과 diff를 직접 열어 읽습니다.

| 점검 항목 | 충족 기준 |
|---|---|
| 사용자 경험 | 누가 무엇을 재미있어할지 한 문장으로 설명할 수 있다. |
| 선택 근거 | 후보를 나열하는 데 그치지 않고 선택 이유를 기록했다. |
| 실습 범위 | 서버·로그인·외부 에셋 없이 구현 가능한 작은 게임이다. |
| 개선 분리 | 일시정지가 최초 버전의 필수 기능으로 들어가지 않았다. |
| 문서 역할 | 기술 상세와 실제 테스트 결과를 미리 작성하지 않았다. |
| 변경 범위 | 참가자 저장소의 `ideation.md`만 변경했다. |

```text
Plan 모드에서 AGENTS.md와 ideation.md를 읽기 전용으로 검토해줘.
사용자·핵심 경험·선택 근거·범위·미결정 사항을
'충족 / 보완 필요 / 미확인'으로 평가하고 문서의 근거를 제시해줘.
다음 단계에서 요구사항으로 바꿀 때 모호한 문장을 짚어줘. 파일은 수정하지 마.
```

## 5. 보완과 재확인

너무 큰 아이디어나 미승인 기능이 있으면 **Plan**에서 요청합니다.

```text
최초 버전의 범위가 너무 넓어. 온라인 순위·사운드·여러 웨이브·일시정지를
제외 범위 또는 후속 아이디어로 분리한 수정안을 보여줘.
공통 경로와 다르게 남는 규칙이 있다면 후속 실습 영향을 설명해줘.
아직 파일은 수정하지 말고 내 승인을 기다려줘.
```

수정안을 확인한 뒤 Interactive에서 “이 수정안을 승인한다. `ideation.md`만 수정하고 diff를 보여준 뒤 멈춰줘”라고 요청합니다.
변경을 다시 읽고 같은 점검표로 확인합니다.

## 6. 완료 승인

- [ ] 참가자가 선택 이유와 제외 범위를 설명할 수 있다.
- [ ] `ideation.md`가 실제로 저장되어 있고 미승인 변경이 없다.
- [ ] 다음 단계에서 결정할 사항이 식별되어 있다.

```text
ideation.md를 승인한다. 검토한 이 파일의 변경만 커밋해줘.
메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고,
본문에 02-01 단계 ID, 변경 내용과 이유, 검토 결과와 실행 검증 미수행 범위를 적어줘.
다른 변경은 포함하지 말고 커밋 결과와 작업 상태를 알려줘.
푸시와 다음 단계 작성은 하지 마.
```

커밋은 실제 변경이 있을 때만 요청합니다. 로컬 커밋은 Public 저장소로의 푸시와 다릅니다.
