# 01-01. Public 저장소와 Copilot app 작업 환경 준비

**1. 준비 · 시작 환경**

[이전: 전체 안내](00-overview.md) · [전체 목차](00-overview.md) · [다음: 문서 구조 정의](01-02-document-design.md)

## 1. 설명

실습 안내 저장소를 복사하지 않고 **자신의 새 Public 저장소**에서 시작합니다. 게임 코드뿐 아니라 개발 문서도 직접 만듭니다.

GitHub 저장소는 원격 이력 저장소, Copilot app 프로젝트는 연결된 작업 대상, 세션은 에이전트와 함께 작업하는 대화와 작업 공간입니다. Worktree 세션은 보통 별도 브랜치를 사용합니다. 화면의 프로젝트 이름만 보고 `main`에서 작업한다고 가정하지 않습니다.

> 확인 범위: 프로젝트 선택과 세션 모드는 [공식 app 문서](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions)로 확인했습니다. 초기 커밋 없는 저장소의 연결 동작은 이 자료 작성 환경에서 직접 재현하지 못했습니다. 아래 첫 경로가 실패하면 오류를 기록하고 대안의 조건을 확인합니다.

## 2. 시작 상태

- [ ] GitHub 계정에 로그인할 수 있고 Public 저장소를 만들 권한이 있다.
- [ ] GitHub Copilot app에 로그인했으며 모델을 사용할 수 있다.
- [ ] 컴퓨터에 Git과 Node.js 24 LTS를 사용할 수 있다.
- [ ] 최신 브라우저와 네트워크를 사용할 수 있다.
- [ ] 실습에서 만든 코드·문서·커밋은 공개될 수 있음을 이해했다.

설치가 필요하면 해당 도구의 공식 설치 절차를 이용합니다. 패키지 관리자나 app의 관리자 권한을 무조건 허용하지 않습니다. 토큰을 대화나 파일에 붙여 넣지 않습니다.

## 3. 실행: 새 저장소 만들기

GitHub 웹에서 **New repository**를 선택합니다.

1. 소유자를 자신의 계정으로 선택합니다.
2. 저장소 이름을 정합니다. 예: `my-space-invaders-lab`.
3. **Public**을 선택합니다.
4. README, `.gitignore`, 라이선스 자동 생성을 선택하지 않습니다.
5. 저장소를 만들고 자신의 저장소 URL을 확인합니다.

이 실습 안내 저장소나 다른 사람의 저장소를 선택하지 않았는지 확인합니다. 라이선스를 선택하지 않았다는 사실이 재사용 권한을 부여한다는 뜻은 아닙니다. 공개 라이선스는 배포 준비 단계에서 선택 여부를 검토합니다.

## 4. 실행: Copilot app 프로젝트와 세션

공식 문서 기준으로 사이드바 **Sessions** 옆 **+**에서 세션을 시작하고, 프로젝트 선택에서 **GitHub**의 자신의 저장소를 선택합니다. 대상 버전의 프로젝트 추가 화면이 따로 있으면 그 화면에서 먼저 연결합니다.

- 실행 위치는 로컬 작업 공간을 선택합니다. 기본은 새 Worktree이며 Cloud sandbox를 요구하지 않습니다.
- 모드는 **Plan**을 선택합니다.
- 모델은 사용 가능한 모델 또는 Auto를 사용합니다. 특정 모델의 동일한 출력을 보장하지 않습니다.

파일 없는 저장소에서 연결이나 세션 생성이 실패하면 반복해서 새 저장소를 만들지 말고 아래 복구 절차를 확인합니다.

작업 세션이 열리면 다음 프롬프트를 입력합니다.

```text
이 프로젝트는 Space Invaders 실습용으로 새로 만든 Public 저장소다.
지금은 준비 상태만 읽기 전용으로 확인해줘.

현재 작업 경로, Git 저장소 여부, 현재 브랜치, origin URL,
최초 커밋 존재 여부, 추적/미추적 파일 상태를 확인해줘.
Git 버전, Node.js 버전, npm 버전도 확인해줘.
비밀정보가 URL이나 출력에 포함되면 그대로 출력하지 말고 가려줘.

기존 게임 코드나 개발 문서가 있거나 origin이 내 실습 저장소가 아니면
그 사실을 알려주고 멈춰줘.
Node.js는 이 실습의 공통 경로인 24 LTS인지 확인해줘.

파일 생성/수정, git init, 커밋, 설치, 원격 변경, 푸시는 하지 마.
준비된 항목과 미확인/문제 항목을 구분해 알려주고 기다려줘.
```

### 예상 결과

자신의 저장소 URL과 작업 브랜치, Git·Node·npm 상태가 표시됩니다. `.git` 같은 Git 메타데이터는 있을 수 있지만 게임 코드와 개발 문서는 없어야 합니다.

아직 의존성 정의 파일이 없으므로 `npm install`을 실행하지 않습니다. `AGENTS.md`도 다음 실습에서 정의·작성합니다.

## 5. 점검·확인

- [ ] GitHub에서 저장소가 Public이고 의도한 소유자·이름이다.
- [ ] app의 origin이 해당 URL이다.
- [ ] 세션 브랜치와 `main`의 차이를 확인했다.
- [ ] 초기 커밋 존재 여부를 사실대로 기록했다.
- [ ] 기존 사용자 작업이 없는 새 실습 공간이다.
- [ ] Git·Node 24·npm을 사용할 수 있다.
- [ ] 에이전트가 파일 변경이나 설치를 하지 않았다.

## 6. 보완: 초기 커밋 없는 저장소에서 막힌 경우

Git Worktree는 기준 커밋이 필요합니다. 다만 app이 이 상황을 자동 처리하는지는 버전에 따라 실제 확인해야 합니다.

**파일 없는 상태는 유지하되 Git에 초기 빈 커밋을 만드는 방법**이 대안입니다. 다음 절차는 Git 관점의 대안이며 app 전체 조작이 리허설된 경로는 아닙니다.

1. 오류 메시지와 app 버전을 기록합니다.
2. app이 제공하는 로컬 저장소 작업 방식으로 빈 저장소를 열 수 있는지 확인합니다.
3. 불가능하면 자신의 컴퓨터에 새 빈 폴더를 만들고 app 프로젝트 선택의 로컬 폴더로 열 수 있는지 확인합니다.
4. 로컬 폴더 세션에서 아래 읽기 전용 프롬프트로 준비 계획을 요청합니다.

```text
원격 Public 저장소에는 아직 커밋이 없어서 세션 준비가 막혔다.
현재 폴더가 새 빈 폴더인지, 기존 Git 저장소인지 읽기 전용으로 확인해줘.
기존 파일이나 다른 저장소가 있으면 중단해줘.

게임 파일을 만들지 않고 초기 빈 커밋만 준비하는 계획을 제시해줘.
필요한 경우에만 git init -b main을 사용하고,
git commit --allow-empty로 초기 커밋을 만드는 방법을 설명해줘.
작성자 설정이 없으면 내 확인을 요청하고 임의의 이름/이메일을 설정하지 마.
원격 URL은 내가 만든 저장소 URL을 확인한 후에만 설정하도록 해줘.
커밋과 원격 푸시를 분리해서 설명하고 아직 실행하지 마.
```

계획이 맞으면 **Interactive**에서 해당 로컬 초기화·빈 커밋만 승인합니다. 한국어 커밋 메시지에 “파일 없이 실습 저장소의 기준 커밋을 준비함”을 명시합니다. `main` 브랜치명과 원격 상태를 다시 확인한 뒤, **별도 승인으로** 초기 커밋을 자신의 원격 저장소에 푸시합니다. 기존 원격 이력이 발견되면 강제 푸시하지 않습니다.

이후 GitHub 프로젝트 연결을 다시 시도합니다. 로컬 폴더 세션 자체를 열 수 없으면 이 대안을 실행 가능하다고 가정하지 말고 진행자에게 화면·오류를 공유하고 중단합니다. CLI나 VS Code로 몰래 전환한 뒤 app에서 성공했다고 기록하지 않습니다.

## 7. 완료 승인

```text
환경 준비 결과를 대화에 정리해줘.
저장소 URL, 작업 브랜치, 도구 버전, 파일 상태,
초기 커밋 유무와 사용한 준비 경로, 남은 제약을 기록해줘.
토큰이나 개인 경로의 불필요한 상세는 포함하지 마.
준비가 완료되지 않았으면 다음 단계로 넘어가지 마.
완료되었더라도 아직 파일을 만들거나 문서 정의를 시작하지 말고 기다려줘.
```

준비 완료 후 다음 실습에서 개발 문서 구조를 정의합니다. 이 단계에서 만든 빈 커밋은 환경 준비용 예외이며, 이후 논의만 한 단계마다 빈 커밋을 만들지 않습니다.
