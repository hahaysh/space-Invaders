# 05-02. 결함 수정과 회귀 검증

[이전](05-01-게임-검증과-Skill.md) · [전체 목차](00-전체-실습-안내.md) · [다음: Pages 배포 준비](06-01-Pages-배포-준비.md)

## 이번 실습

실제 검증에서 발견한 문제만 고치고 기존 기능이 유지되는지 확인합니다.
모든 필수 기능이 이미 맞으면 수정 루프 없이 배포 준비로 넘어갑니다.
테스트 숫자를 늘리는 것이 아니라 수용 기준의 빈틈을 없애는 것이 목표입니다.

## 시작 전

- 같은 검증·첫 배포 이슈 세션을 사용합니다.
- `TEST_PLAN.md`와 실제 `TEST_RESULTS.md`가 있습니다.
- Skill 인식·호출 확인 상태를 알고 있습니다.

## App Plan: 결과 분류

```text
TEST_RESULTS와 실제 로그를 PRD의 필수 수용 기준과 대조해 줘.
실제 결함·검사 누락·환경 실패·미실행을 구분하고 필요한 수정만 제안해 줘.
시작/이동/발사/적/충돌/점수/승패/재시작 전체의 확인 경로를 살펴봐 줘.
검사 수나 비공개 함수명에 맞추지 말고 동작이 검증되는지 판단해 줘.
통과한 경우 가상 버그나 불필요한 변경 없이 배포 준비 가능 여부를 알려 줘.
코드 수정과 새 원격 이슈 생성은 아직 하지 마.
```

검사 실패는 곧 제품 결함이라는 뜻은 아닙니다.
예를 들어 브라우저 실행 파일이 없으면 설치 환경 문제이며 게임 규칙 실패와 다릅니다.
외부 스크립트가 있다고 추측만 한 내용을 실제 버그로 기록하지 않습니다.

## 실제 결함이 있을 때만 실행

App **Interactive**로 바꾸고 계획 범위를 승인합니다.

```text
확인된 결함의 최소 수정을 승인해.
실패를 재현하는 검사를 유지/추가하고 관련 코드만 수정해 줘.
game-check Skill을 사용해 관련 검사와 필수 기능 회귀를 실제 실행해 줘.
Skill 미인식이면 명시적 읽기 대체 실행임을 정직하게 표시해 줘.
TEST_RESULTS에는 실패→수정→재실행 근거와 남은 미확인을 짧게 기록해 줘.
기대값 삭제·통과 조작·새 기능 추가는 하지 마.
```

별도로 추적할 실제 결함이면 같은 이슈에 체크 항목을 추가하거나 버그 이슈 하나를 만들 수 있습니다.
간단한 수정마다 새로운 보고서 파일·이슈·세션을 만들 필요는 없습니다.
모든 검사 통과 시에는 현재 증거를 검토하고 아래 완료 기준으로 바로 이동합니다.

## 실제 브라우저와 빌드

Node 검사는 제어 가능한 시간으로 충돌·종료·초기화 경계를 확인합니다.
Playwright는 실제 키·버튼과 화면 연결을 확인합니다.
실제 사람이 눌러 본 항목은 자동 브라우저 조작 결과와 따로 남깁니다.
기본 기능에 대한 확인 방법이 전혀 없는 항목을 통과로 묶지 않습니다.
빌드 결과를 preview 4173에서 확인하고 저장소 하위 경로의 자산 로딩도 검사합니다.
긴 정지나 포트 충돌은 세션이 소유한 실행만 다루고 호스트 원인을 단정하지 않습니다.

## 눈으로 확인

- [ ] 모든 필수 기능에 실제 자동/수동 확인 근거가 있습니다.
- [ ] 결함 수정 전 재현과 수정 후 관련 회귀 결과가 있습니다(결함 없으면 해당 없음).
- [ ] Node 규칙 검사와 브라우저 실제 입력 확인이 구분됐습니다.
- [ ] 빌드·하위 경로 검사를 실행했고 오류·미실행을 숨기지 않았습니다.
- [ ] 계획/결과 문서가 실제 변경과 맞으며 실패 검사를 지워 숨기지 않았습니다.

## 필요할 때만 보완

```text
아직 확인 근거가 없는 필수 항목만 골라 가장 작은 검사를 실제 실행해 줘.
실행할 수 없다면 이유를 기록하고 배포를 막는지 알려 줘. 성공을 추정하지 마.
```

## 완료

필수 기능이 맞고 배포를 막는 결함이 없을 때 검토한 변경을 커밋합니다.
계획 표와 이슈에 현재 검증 상태를 짧게 남깁니다.
아직 공개 URL이 없으므로 배포 이슈는 열린 채로 06으로 이어갑니다.
