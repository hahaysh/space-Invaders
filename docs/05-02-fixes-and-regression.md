# 05-02. 결함 수정과 회귀 검증

**5. 검증 · 재현 → 최소 수정 → 재검증**

이전: [05-01 요구사항 테스트](05-01-requirements-testing.md) · [전체 목차](00-overview.md) · 다음: [06-01 배포 준비](06-01-deployment-setup.md)

## 1. 설명

수정 효과를 원래 재현 절차로 확인하고 연결된 기존 기능도 다시 확인하는 것이 **회귀 검증**입니다.
이번에는 모든 문제를 한꺼번에 맡기지 않고 우선순위가 높은 결함 하나씩 진행합니다.
요구사항을 느슨하게 바꾸거나 실패 테스트를 삭제하는 것은 결함 수정이 아닙니다.

실패가 없다면 억지로 코드를 바꾸지 않습니다. 남은 미확인의 증거를 확보하고 최종 검증 상태를 정리합니다.

## 2. 시작 상태

- [ ] `TEST_PLAN.md`와 실제 `TEST_RESULTS.md`를 참가자가 검토했다.
- [ ] 실패·미확인·검증 대상 커밋을 구분하고 현재 지침·PRD·TRD·구현 계획을 확인했다.
- [ ] 세션·브랜치·기존 변경과 로컬 서버 상태를 확인했다.
- [ ] Copilot app의 **Plan** 모드를 선택했다.

## 3. 실행: 한 결함씩 닫기

### 3-1. Plan에서 실패와 차단 원인 분류하기

```text
AGENTS.md, PRD.md, TRD.md, IMPLEMENTATION_PLAN.md,
TEST_PLAN.md, TEST_RESULTS.md와 관련 코드·테스트를 읽어줘.
파일 변경·명령 실행·설치·커밋·푸시 없이 수정 후보를 정리해줘.
결함 ID, 관련 REQ/TC, 기대/실제 결과, 재현 절차, 근거,
영향, 우선순위, 최소 변경 파일, 재검증 방법을 표로 보여줘.
제품 결함, 테스트 자동화 누락/오류, 환경 차단, 단순 미확인을 구분해줘.
미확인은 기능 실패라고 단정하지 말고 필요한 관찰을 제시해줘.

먼저 처리할 결함 하나를 추천하고 원인 가설과 수정안을 설명해줘.
가능하면 수정 전 실패를 재현하는 회귀 테스트를 먼저 추가하는 순서를 제안해줘.
테스트 기대값은 승인된 PRD가 기준이며 구현에 맞추어 완화하지 마.
범위 밖 기능이나 CHG-01 일시정지, 대규모 재구성은 제안에서 제외해줘.
실패가 없으면 코드 수정 없음이라고 하고 남은 검증 계획만 제시해줘.
실제 작업은 내 승인을 기다려줘.
```

참가자가 가장 먼저 처리할 결함을 선택합니다. 아래 예시는 원인이 확인된 후에만 채택합니다.

```text
한 탄환으로 적 둘이 제거되는 결함부터 처리하자.
충돌 반복문에서 탄환이 소모된 뒤 처리가 이어지는지 확인하고,
한 탄환과 겹치는 두 적으로 재현할 순수 테스트를 제안해줘.
최소 변경 파일과 관련 REQ-05 회귀 범위를 보여줘. 아직 파일은 수정하지 마.
```

### 3-2. Interactive에서 선택한 수정과 검증 실행하기

```text
방금 검토한 결함 하나의 수정 계획만 승인한다.
AGENTS.md를 읽고 승인 목록의 코드·테스트 파일만 수정해줘.
가능한 경우 회귀 테스트를 먼저 추가하고 수정 전 실제 실패를 확인해줘.
재현되지 않으면 추정 수정하지 말고 근거와 추가 조사 방법을 보고하고 멈춰줘.
그다음 최소 구현 수정을 적용하고 같은 테스트의 실제 통과를 확인해줘.
명시적 dt로 경계를 검증하고 운영 코드에 테스트용 window 치트를 추가하지 마.

관련 테스트 실행 후 npm test, npm run test:e2e, npm run build로 회귀 확인해줘.
E2E는 설정된 webServer를 사용하고 포트 충돌 때 다른 프로세스를 종료하지 마.
통과를 위해 테스트 삭제·skip·기대값 완화·PRD 변경을 하지 마.
추가 변경이나 의존성 설치가 필요하면 이유를 설명하고 새 승인을 기다려줘.

TEST_RESULTS.md에 기존 실패를 지우지 말고 새 검증 회차를 추가해줘.
결함 ID·REQ/TC, 변경 파일, 수정 전후 실행 증거, 대상 커밋과 미커밋 변경,
회귀 결과, 수동 확인 대기 항목을 기록해줘.
실제 결과만 통과(pass)/실패(fail)/미확인(unverified)으로 적어줘.
TEST_PLAN.md는 승인한 회귀 TC 추가만, IMPLEMENTATION_PLAN.md는 해당 상태만 갱신해줘.
diff와 결과를 보여주고 멈춰줘. 다른 결함·커밋·푸시·배포는 진행하지 마.
```

환경 차단은 승인한 복구·재실행만 합니다. Chromium 누락은 Playwright 설치 확인 후 `npx playwright install chromium`으로 해결합니다.
실패한 검사 실행과 복구 후 실행을 모두 남기고, 실제로 못 확인한 항목은 미확인을 유지합니다.

### 3-3. 참가자 재현과 결함별 승인

승인된 로컬 서버 명령을 app에서 에이전트에게 요청하고 실제 응답 URL을 확인합니다.
원래 실패한 조작과 연결된 입력·점수·승패·재시작을 직접 반복합니다.
관찰 내용을 전달해 결과 문서에 반영하도록 요청한 뒤 코드·테스트·문서 diff를 함께 읽습니다.

```text
이 결함의 원래 재현 절차와 관련 기능을 직접 확인했다.
방금 전달한 관찰만 TEST_RESULTS.md에 반영하고 최종 diff를 보여줘.
다른 결함은 시작하지 말고 커밋·푸시하지 마.
```

diff 승인 후 “이 결함의 변경만 커밋하고 푸시하지 마. 메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고, 본문에 05-02 단계 ID와 결함 ID, 변경 내용과 이유, 실제 회귀 검증 결과와 미확인 범위를 적어줘”라고 요청합니다.
다른 결함이 남으면 다시 Plan으로 돌아가 하나씩 같은 절차를 반복합니다.

### 예상 결과

- 재현 근거와 회귀 테스트를 갖춘 최소 수정 또는 정당한 “코드 수정 없음”.
- 과거 실패와 새 검증 회차가 함께 남은 `TEST_RESULTS.md`.
- 기능 준비 상태와 남은 미확인·차단 요인의 명확한 구분.

## 4. 함께 점검·확인

| 점검 항목 | 충족 기준 |
|---|---|
| 재현 | 무엇이 실패했고 어떤 변경으로 해결됐는지 설명할 수 있다. |
| 회귀 | 수정 기능뿐 아니라 전체 순수/E2E 검사와 빌드를 다시 수행했다. |
| 핵심 경계 | 한 탄환·한 적, 중복 점수 없음, 종료 정지·완전한 재시작이 유지된다. |
| 기록 | 이전 실패를 삭제하지 않고 새 실행 대상·결과를 식별한다. |
| 범위 | 미승인 요구사항 변경·새 기능·불필요한 패키지가 없다. |

## 5. 보완과 재확인

```text
Plan에서 최근 수정 diff와 실제 회귀 결과를 읽기 전용으로 검토해줘.
테스트가 새 버그를 놓치거나 기존 수용 기준을 완화한 부분이 있는지 확인해줘.
남은 실패와 미확인은 분리하고, 필요한 최소 재검증 또는 수정안을 제안해줘.
코드·문서 수정과 재실행은 새 승인 전까지 하지 마.
```

간헐 실패는 “한 번 통과”로 닫지 않습니다. dt·입력·서버 상태 등의 재현 조건을 확인하고 다시 승인받습니다.
관찰과 자동 테스트가 다르면 둘 다 기록한 채 원인을 조사합니다.

## 6. 완료 승인

- [ ] 필수 로컬 수용 기준에 열린 실패나 검증 차단이 없다.
- [ ] 미확인으로 남은 항목은 아직 수행하지 않은 공개 배포 확인처럼 이유가 명확하다.
- [ ] 실제 최종 코드의 자동 검사·빌드·수동 결과를 확인했다.
- [ ] 승인된 변경만 커밋했고 생성물·비밀 정보는 포함하지 않았다.

```text
현재 결과로 로컬 검증 단계를 승인한다.
REQ-01~08별 최종 상태와 증거, 06단계에서 확인할 공개 배포 항목을 대화에 정리해줘.
검토한 최종 기록 변경이 남으면 그 파일만 커밋해줘. 메시지는 너무 짧지 않은 한국어 설명형 제목과 본문으로 작성하고, 본문에 05-02 단계 ID, 변경 내용과 이유, 실제 최종 검증 결과와 미확인 범위를 적고 커밋 결과를 알려줘.
변경이 없으면 빈 커밋을 만들지 마. 푸시·PR·병합·배포는 하지 마.
이번 실습에서 시작한 서버만 종료하고 다음 요청을 기다려줘.
```

공개 배포 성공은 아닙니다. 다음 단계에서 Pages 설정·PR 검토·`main` 병합·Actions·공개 URL을 별도로 확인합니다.
